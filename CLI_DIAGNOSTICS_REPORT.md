# Отчёт: безопасность CLI и эксплуатационная диагностика (волна 10)

Дата: 2026-11-01. Стенд: Debian, киоск `openscale-kiosk` (пользователь `administrator`),
БД `/home/scales/plu.db` (WAL, 218 товаров).

## 1. Аудит CLI-команд, работающих с БД

Единая точка доступа — `backup::CliDb::open(cfg, exclusive, allow_create)`:
flock обслуживания + `probe_startup` (маркер, integrity, миграции, чтение данных) +
открытие через SQLite URI `mode=rw` (строго без создания). Ни одна CLI-команда
больше не открывает рабочую БД напрямую через `datastore::open`.

| Команда | БД | Блокировка | Создание | Миграции | Поведение при отсутствии/повреждении |
|---|---|---|---|---|---|
| `--sync` (apply_upload) | да, запись | SH | только первичная установка (нет маркера) | да (доп.) | отказ: «БД недоступна…», данных нет |
| `--import plu.xml` | да, запись | SH | только первичная установка | да (доп.) | отказ, файл не создаётся |
| `--dept-add/-style/-remove/-move/-group-assign` | да, запись | SH | только первичная установка | да (доп.) | отказ |
| `--backup` | да, чтение | SH (+лок каталога) | нет | да (доп.) | «базы нет, копировать нечего» |
| `--restore` | замена файла | **EX** | нет (кроме записи pre-restore копии) | да (после замены) | отказ до любых изменений |
| `--db-check` | да, чтение | SH | нет | да (доп.) | отказ с причиной |
| `--diag` | да, чтение | SH | нет | да (доп.) | строка «ошибка: …» в отчёте |
| `--calibrate` | да, чтение+калибровка | SH | только первичная установка | да (доп.) | отказ |
| `--weight`, `--label-probe`, `--version` | нет | нет | нет | нет | не зависят от БД |

Внутрипроцессные `datastore::open` киоска (settings/admin/flow/tick/print) не являются
CLI: киоск уже держит SH-блокировку процесса, а его торговые обработчики закрыты
guard'ом `db_unavailable` (волна 9).

Замечание о миграциях: открытие через `datastore::open` при Ready может применить
отложенные аддитивные миграции даже в «диагностической» команде. Это безопасно
(схема только расширяется), зафиксировано как свойство, а не обход.

## 2. Закрытые обходы fail-closed

- `--sync`: `sync::apply_upload` шёл в `datastore::open` напрямую — при потерянной
  установленной БД создал бы пустую. Теперь через `CliDb::open` (SH, allow_create):
  при маркере без файла — «БД недоступна, операция отменена», файл не создаётся;
  создание допустимо только при отсутствии маркера (первичная установка), после
  создания пишется маркер.
- `--import`, `--dept-*`, `--calibrate`: та же схема.
- `--db-check`, `--diag`, `--backup`: создание запрещено всегда (allow_create=false).

Авто-синхронизация киоска (`spawn_auto_sync`) идёт через тот же `apply_upload` —
защищена тем же механизмом без дублирования логики.

## 3. Блокировки

- Работающий киоск: SH на всё время; занимает ли его диагностическая команда — да,
  SH+SH совместимы, торговля не блокируется (проверено на стенде: `--diag` и
  `--db-check` при active-киоске прошли, `integrity_check: ok`, 218 товаров).
- Запись CLI (sync/import/dept/calibrate): SH — координация записи внутри SQLite
  (busy_timeout), торговлю не блокирует.
- `--restore`: EX — исключает и киоск, и второе восстановление, и CLI-запись.

## 4. Диагностика для поддержки (`--diag` дополнен)

- База PLU: «ок, N товаров» / «база ещё не создана (первичная установка)» /
  «ошибка: БД недоступна…» с точной причиной;
- резервные копии: имя последнего снимка и возраст («1 ч назад») либо подсказка
  выполнить `--backup`;
- весы и принтер: состояние порта (принтер, занятый киоском, честно помечен ошибкой
  захвата — это признак работающего киоска, а не аварии);
- набор от центра: uploading/ready/plu.xml состояние.

## 5. Проверки

Автотесты (весь набор 219 passed): 5 новых:

- диагностическое чтение отказывается от первичной установки;
- создание только при первичной установке + маркер;
- отказ на повреждённой БД;
- путь записи apply_upload через безопасный механизм работает.

Стенд (sha256 последнего деплоя, все команды sudo):

- БД отложена в сторону (маркер жив): `--import` → «база потеряна», `--dept-list` →

  копировать нечего»; файл `/home/scales/plu.db` после всех команд — отсутствует

- БД возвращена → киоск active, 218 товаров, integrity ok.

## 6. Ограничения

1. `--sync` при отсутствии связи с центром не доходит до БД — отказ применения
   проверен через `--import` (тот же `CliDb::open`) и автотестами; живой прогон
   `--sync` на потерянной БД требует подключения центра.
2. Миграции при диагностическом открытии — свойство существующего `datastore::open`
   (store не переписывался по ограничению волны); аддитивные, риска нет.
3. `--diag` при active-киоске показывает принтер как занятый — ожидаемо, формулировка
   сохранена как есть.
