# Динамические раскладки этикеток: конструктор на ПК, автодетект размера по зазору

Дата: 19.10.2026. Статус: согласован с заказчиком.

## Проблема

Раскладка этикетки зашита константой (`LIVE_LAYOUT`, 448×232 дот). Заказчик
использует этикетки четырёх размеров (узкая, средняя, почти квадратная,
длинный прямоугольник); при смене рулона печать «кривая». Нужны раскладки
под каждый размер, загружаемые на весы без перепрошивки, и автоматический
выбор раскладки под заправленный рулон.

## Решения заказчика

- Конструктор — на ПК, один offline HTML-файл; умеет открыть существующий
  JSON, править, создавать новые. На будущем сервере управления весами —
  отдельная задача (бэклог), сейчас вне объёма.
- Весы сами определяют размер этикетки по датчику зазора (ручной выбор
  размера не делаем).
- Несовпадение измеренного размера ни с одной раскладкой — печать по
  ближайшей + предупреждение персоналу (продажу не блокируем).
- Состав полей: name, plu, barcode, weight, price, sum, date, time,
  shelflife («Годен до ДД.ММ.ГГГГ»), cardprice (печатается только при
  загруженной скидочной цене), text (статическая надпись из JSON).

## 1. Формат файла раскладки

`label-<имя>.json` в каталоге обмена `[kiosk] cfg_export_dir` (как конфиг).

```json
{
  "format": 1,
  "name": "58x40",
  "width_mm": 58,
  "height_mm": 40,
  "fields": [
    { "kind": "name",  "x": 2,  "y": 1, "font": "A", "size": 1 },
    { "kind": "shelflife", "x": 30, "y": 12, "font": "B", "size": 1 },
    { "kind": "text", "text": "СПАСИБО ЗА ПОКУПКУ", "x": 10, "y": 36, "font": "B", "size": 1 }
  ]
}
```

- Единицы — миллиметры; весы переводят в доты (VKP80II 203 dpi, шаг
  уточняется спайком датчика; константа в одном месте кода).
- Валидация импорта: `format == 1`; обязательные поля kind: name, weight,
  sum, barcode; x/y в границах этикетки; поле text — непустой текст ≤ 48
  символов; неизвестный kind — ошибка импорта (не молча игнор).
- `cardprice`: если у товара нет `card_price` — место остаётся пустым,
  это не ошибка.
- Имя файла = `name` из содержимого (переименование только в конструкторе).

## 2. Движок печати

- `build_label` получает раскладку (список полей + размеры области) вместо
  `LIVE_LAYOUT`. Поля данных берут значения из товара/печати; `text` — из
  самой раскладки.
- Реестр — таблица `label_layouts` в БД (name, width_mm, height_mm, json,
  created_at). Импорт: INSERT OR REPLACE по имени.
- Нет ни одной загруженной раскладки → стоковая `LIVE_LAYOUT` (нынешнее
  поведение сохраняется как fallback).

## 3. Автодетект размера по зазору

- Спайк на стенде до реализации движка: команда опроса датчика зазора
  VKP80II (ESC/POS-статус), шаг подачи (дот/мм), надёжность измерения.
  Результат спайка фиксируется в FIXLOG и уточняет этот раздел.
- Измерение: при старте задания печати — подача до следующего зазора с
  подсчётом шагов; длина = шагов / (дот/мм). Измеренное кэшируется;
  перезамер — после аварии бумаги/открытия крышки и по кнопке
  «Проверить этикетку».
- Подбор: |измерено − height_mm| ≤ 3 мм → раскладка; иначе ближайшая по
  высоте + предупреждение персоналу в статусной строке (продажа идёт).
- Таймаут измерения 3 с; не ответило → кэш или сток (инвариант «программа
  не зависает», печать не ждёт вечно).

## 4. Конструктор (один HTML-файл)

- `tools/label-designer.html`: сетка по миллиметрам под заданный W×H,
  drag-and-drop полей мышью, выбор шрифта (A/B) и размера (1/2),
  редактирование текста static-полей, поля-образцы с примерными данными
  (название, вес, цены, «Годен до»).
- Кнопки: «Создать» (размер в мм), «Открыть JSON» (правка существующей),
  «Скачать JSON». Без сервера, зависимостей и сборки — один файл.
- Вид полей в конструкторе приближён к принтеру: моноширинный текст,
  size 2 — двойная высота/ширина, штрихкод — прямоугольник пропорции EAN-13.

## 5. Меню весов

«Оборудование» → «Этикетки»:
- список загруженных раскладок (имя, W×H мм, число полей);
- импорт из каталога обмена (по образцу импорта конфига: превью →
  применить);
- удаление;
- «Проверить этикетку» — измерить сейчас, показать измеренный размер и
  выбранную раскладку.

## 6. Ошибки и деградация

- Импорт невалидного JSON — попап с причиной, реестр не меняется.
- Датчик не ответил/не распознан — кэш прошлого измерения, иначе сток.
- Нет раскладок — сток. Удалять последнюю раскладку можно (возврат к стоку).

## 7. Тестирование

- Unit: парсер JSON раскладки (валид/невалид/неизвестный kind), подбор
  раскладки по измеренной длине (попадание/допуск/ближайшая), перевод
  мм→доты; build_label с кастомной раскладкой (позиции полей в байтах).
- Стенд: измерение на всех четырёх размерах рулонов, печать боевой
  этикетки каждым размером, импорт/удаление через меню.

## 8. Порядок работ

1. Спайк датчика (команда, шаг, точность).
2. Движок раскладок: парсер, реестр, build_label от раскладки, подбор.
3. Импорт и экран «Этикетки».
4. Конструктор HTML.
5. Стенд-прогон всех размеров.

## Вне объёма

- Конструктор на сервере управления весами (бэклог заказчика).
- Линии/рамки/картинки на этикетке (не поддерживается escpos-движком —
  отдельная задача, если потребуется).
- Ручной выбор размера раскладки в меню.
