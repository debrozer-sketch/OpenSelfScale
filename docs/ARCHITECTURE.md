# Архитектура ScaleFW

## Слои

```
┌─────────────────────────────────────────────┐
│ Центральный конфигуратор (TypeScript)       │  визуальный редактор
│ веб, вне весов                              │  этикеток/кнопок, парк
└──────────────┬──────────────────────────────┘
               │ FTP/выгрузка XML (drop) или FTP-pull
┌──────────────▼──────────────────────────────┐
│ kiosk: модуль sync (app/kiosk/src/sync.rs)  │  приём выгрузки: watch
│                                             │  ready.flg → import →
│                                             │  archive → cleanup
├─────────────────────────────────────────────┤
│ datastore (Rust)       crates/datastore     │  SQLite PLU, импорт XML
├─────────────────────────────────────────────┤
│ shtrih-m (Rust)        crates/shtrih-m      │  весы: 115200, LRC, опрос
│ escpos (Rust)          crates/escpos        │  принтер: 19200, page mode,
│                                             │  статус-мониторинг
├─────────────────────────────────────────────┤
│ kiosk (Rust+Slint)     app/kiosk            │  UI, поток веса, печать,
│                                             │  диагностика, калибровка
└─────────────────────────────────────────────┘
```

## Решения и почему

1. **Rust в контуре, TS в центре.** Контур 24/7 на J1900/4 ГБ: без GC,
   без зависимостей в рантайме, один бинарник. Тяжёлый визуальный редактор
   живёт на сервере, где железо не ограничено.
2. **Крейт на устройство.** Драйверы изолированы, тестируются на байтах из
   реального дампа без железа, переиспользуются в CLI-утилитах и тестовом
   стенде.
3. **Drop-протокол как в старом ПО.** Сервер магазина сам пушит выгрузку
   (plu.xml + layout.xml + картинки + ready.flg) в каталог приёма; киоск
   следит за каталогом и применяет данные без рестарта. Гонка флага/данных
   старого конвейера (PROBLEMS Б2) закрыта ожиданием стабильности размеров
   и уважением uploading.flg. Запасной pull-режим — FTP из киоска.
4. **Статус-мониторинг обязателен.** disableStatusCheck=1 в старом ПО —
   источник недопечаток и двойной подачи (PROBLEMS А1/А2). В киоске:
   опрос статуса принтера раз в 10 с (порт делится с печатью через
   мьютекс), сводный индикатор — статус-полоса UI.
5. **Калибровка — процедура, не константы.** Прогон тестовых этикеток,
   подтверждение оператором, хранение в БД.
6. **Весовой поток не роняет UI.** Ошибка порта = PortDown в снапшоте
   и переподключение (лечит креш-циклы старого while true).

## Поток взвешивания

```
weight-poll thread ──(poll_once ~1 Гц)──> Snapshot{mass_kg, stable, port_up}
        UI timer 100 мс ──читает──> экран (вес, статус-полоса)
        selected(plu) ──> lookup PLU ──> build_label ──> escpos печать
                                        └──> status() ──> лог/индикация
```

## Статус

Крейты shtrih-m, escpos, datastore — реализованы с тестами на живых байтах;
kiosk — рабочий киоск (UI, drop-синхронизация, печать, диагностика); центр —
следующий этап (ROADMAP).
