# Канонический формат выгрузки товаров

Контракт для сторонних интеграций: любой источник данных (ERP, обменник,
самописный экспорт) подключается к весам без правки их исходников.
Актуальная версия формата — 1.

## Как это работает

Весы поддерживают три протокола приёма (`[center].protocol` в config.toml):

| protocol    | откуда данные                                       | формат        |
|-------------|-----------------------------------------------------|---------------|
| `drop`      | источник сам кладёт файлы в incoming_dir + ready.flg| старый plu.xml|
| `ftp`       | весы сами тянут по FTP ([center].host, plu_path)    | старый plu.xml|
| `external`  | источник кладёт СВОЙ файл + ready.flg, весы запускают конвертер | любой |

Внешний конвертер (`[center].external_cmd`) — программа/скрипт на чём
угодно, которую пишет сторона интеграции:

- аргумент при запуске: путь к файлу поставщика (`[center].external_input`,
  по умолчанию кладётся рядом с ready.flg в incoming_dir);
- вывод на stdout: канонический JSON (см. ниже);
- код возврата 0 — успех; код возврата != 0 или работа дольше 60 с —
  выгрузка не принимается, каталог приёма не чистится, источник может
  перезалить.

Картинки товаров доставляются тем же конвейером, что и в старом протоколе:
файлы `<PLU>.jpg` / `<PLU>.png` в incoming_dir зеркалируются в
`[center].img_local_dir/plu`. Конвертер картинки не обрабатывает.

## Формат

JSON-массив товаров. Обязательны три поля, остальные — опциональные:
отсутствие любого опционального поля НЕ ломает выгрузку, соответствующая
функция просто не работает для этого товара.

```json
[
  {
    "plu": "2502192",
    "name": "ВИНОГРАД КИШМИШ ЧЕРНЫЙ КГ",
    "price_kop": 19999,
    "itemcode": "02136",
    "card_price_kop": 17999,
    "group": "ФРУКТЫ",
    "name_second": "сорт: кишмиш",
    "shelf_life": "20/09/2026 18:25:45"
  }
]
```

| поле             | тип    | обяз. | смысл и деградация при отсутствии |
|------------------|--------|-------|------------------------------------|
| `plu`            | string | да    | код товара (PLU). Пустой — запись пропускается |
| `name`           | string | да    | название на экране и этикетке. Пустое — запись пропускается |
| `price_kop`      | int    | да    | цена за кг в копейках (19999 = 199,99). Отрицательная — запись пропускается |
| `itemcode`       | string | нет   | код для штрихкода EAN-13 (последние 5 цифр). Нет — штрихкод строится из нулей, весовая часть остаётся корректной |
| `card_price_kop` | int    | нет   | цена по карте в копейках. 0 или нет — скидочной цены нет |
| `group`          | string | нет   | товарная группа для навигации. Нет — попадёт в «ПРОЧЕЕ» |
| `name_second`    | string | нет   | вторая строка названия. Нет — не печатается |
| `shelf_life`     | string | нет   | строка срока годности как есть (печатают на этикетке). Нет — строка не печатается |

## Семантика выгрузки

- Выгрузка — полное зеркало каталога: товары, которых нет в файле,
  снимаются с учёта (`remove_absent`), как в старом протоколе.
- Битые записи (пустой код/имя, отрицательная цена) пропускаются со
  счётчиком в журнал; выгрузка не принимается только если валидных
  записей не осталось вообще.
- Раскладка по отделам в каноническом формате не передаётся: привязка
  «группа → отдел» правится на весах (импорт конфигурации, CLI
  `--dept-assign`, SQL). Группы без привязки уходят в «ПРОЧЕЕ».

## Пример конвертера

```python
#!/usr/bin/env python3
# vendor-to-canonical.py: CSV поставщика → канонический JSON
import csv, json, sys

rows = []
with open(sys.argv[1], encoding="cp1251", newline="") as f:
    for r in csv.DictReader(f, delimiter=";"):
        rows.append({
            "plu": r["CODE"].strip(),
            "name": r["TITLE"].strip(),
            "price_kop": round(float(r["PRICE"]) * 100),
        })
json.dump(rows, sys.stdout, ensure_ascii=False)
```

config.toml:

```toml
[center]
protocol = "external"
external_cmd = "/usr/local/bin/vendor-to-canonical.py"
external_input = "vendor.csv"
```
