# Отчёт: аварийное восстановление, резервирование и обновление (волна 8)

Дата: 2026-11-01. Стенд: Debian, systemd, БД `/home/scales/plu.db` (WAL, 218 товаров).

## 1. Состояние эксплуатации (проверено, без изменений)

- systemd `openscale-kiosk.service`: `Restart=always`, `RestartSec=3`, отдельный пользователь,
  `RuntimeDirectory=openscale-kiosk`, umask 077 в старт-скрипте — при `kill -9` процесс поднимается
  сам (проверено, §5).
- БД: SQLite WAL, `synchronous=NORMAL`, busy_timeout 5 с; миграции идемпотентны
  (`IF NOT EXISTS` + ALTER + реплейс в транзакции), кэш миграций per-path.
- Права: БД 0600 (PIN-хеши), каталог БД принадлежит сервисному пользователю.

## 2. Резервное копирование (новое, `src/backup.rs`)

- Снимок — SQLite Backup API (`Connection::backup`): единый согласованный файл, учитывающий WAL,
  выполняется на живой БД без остановки торговли.
- После снимка: `PRAGMA integrity_check` копии; копия без ключевых таблиц (`plucodes`,
  `print_log`, `app_settings`) отклоняется.
- Ротация: не более 10 копий (`openscale-YYYYMMDD-HHMMSS.db`), имена без точек, уникальны
  при нескольких снимках в секунду; последняя заведомо исправная копия не удаляется (кандидаты
  проверяются перед удалением).
- Одновременность: lock-файл `create_new`; lock старше 10 минут считается оставшимся после
  краха и снимается.
- Побочные файлы снимка (0-байтовый WAL, SHM) удаляются.
- Ошибки — в лог (`log::error`/`warn`), торговлю не останавливают.

Команды администратора:
```
openscale --db-check              # integrity_check + статистика (товары, отделы, печати, пользователи)
openscale --backup [КАТАЛОГ]      # снимок + ротация; по умолчанию <каталог БД>/backups
openscale --restore ФАЙЛ          # восстановление (см. §3)
```

Автоматика: киоск раз в час проверяет возраст последнего удачного снимка; раз в сутки создаёт
новый (best-effort, только лог). Поток `backup-daily` не касается UI и торговли.

## 3. Восстановление (CLI `--restore`, только вручную)

Порядок гарантий:
1. При работающем киоске (`systemctl is-active` или живой не-zombie процесс) — отказ до любых
   изменений. (Отладка: сообщение перечисляет найденные процессы.)
2. Снимок проверяется (`integrity_check` + схема) до замены.
3. Текущая БД (даже повреждённая) сохраняется: `pre-restore-<имя>.db` + WAL/SHM рядом.
4. Замена атомарна: снимок → `restore.tmp.db` (та же ФС) → `rename`; старые WAL/SHM удаляются
   (несовместимы с заменённой базой).
5. После замены: открытие (прогон миграций) + `load_all`; при неудаче исходная база
   возвращается на место, операция завершается ошибкой — база никогда не остаётся
   в неопределённом состоянии.
6. Автоматического восстановления при обычном запуске нет — только явное решение администратора.

## 4. Надёжное обновление (`deploy/push.py --deploy`)

Механизм (вместо прежнего «голого» put + ручная установка):
1. Загрузка во временный файл `install/openscale.new`.
2. Сверка размера и sha256 локально и на весах.
3. Проверка запускаемости: `openscale.new --version` (после chmod; файл без права исполнения
   уже однажды отвергнут на практике — защита сработала при первом прогоне).
4. Текущий бинарник сохраняется как `openscale.prev`.
5. Замена атомарна: копия в `/usr/local/lib/openscale.staging` (та же ФС) → `mv -f`.
6. `systemctl restart` + `is-active`.
7. При неудачном запуске — автоматический возврат `openscale.prev` и повторный рестарт;
   пользовательские данные не затрагиваются.

Ограничение совместимости: откат бинарника не откатывает схему БД. Все миграции построены
только на расширение (ALTER ADD COLUMN, реплейс с сохранением данных), схема не разрушается,
но гарантий обратной совместимости старого бинарника с новой схемой нет — это зафиксировано:
если новая версия меняла схему несовместимо, возврат `openscale.prev` требует решения
администратора (восстановление из снимка `--restore`), а не молчаливой замены файла.

## 5. Проверенные сценарии

Автотесты (`cargo test -p openscale --lib backup`, 7 шт.; весь набор 209 passed):
- снимок валиден, данные внутри, ротация держит лимит;
- ротация не удаляет последнюю исправную копию;
- второе копирование при активном lock отклоняется;
- восстановление: данные возвращаются к снимку, текущее состояние сохранено как pre-restore,
  база согласована (`integrity_check: ok`) после замены;
- отказ восстановления из повреждённого снимка — рабочая база не тронута;
- отказ при снимке без схемы БД;
- крах с незакрытым соединением: зафиксированная транзакция остаётся только в WAL —
  после повторного открытия данные на месте (восстановление SQLite WAL).

Стенд (sha256 `30f584ba…`):
- `kill -9` киоска при активной БД → systemd поднял сам, `--db-check`: integrity ok, 218 товаров;
- `--backup` на остановленном киоске: снимок без побочных файлов;
- `--restore` из снимка: восстановлено, pre-restore сохранён, киоск запущен, каталог на месте;
- деплой файла без права исполнения → обновление отменено, работающий бинарник не тронут;
- деплой не-бинарника (прошёл контрольную сумму как файл) → «не запускается», обновление
  отменено, сервис active;
- обрыв загрузки (несовпадение размера) → обновление отменено.

## 6. Ограничения

1. Нехватка места на диске в тесте не моделируется; код-пыт покрыт соседним отказом
   (снимок/восстановление при ошибке удаляют временные файлы и возвращают ошибку, торговля
   продолжается).
2. Миниатюры: 2 изображения в каталоге стенда — BMP в файлах `.jpg` (поддержка формата не
   заявлена); к продаже не относятся, зафиксировано ранее.
3. При недоступной БД киоск стартует с пустым каталогом (лог ERROR): автоматическое
   восстановление запрещено требованиями; администратору — `--db-check`, затем `--restore`.
4. Побочные `-shm`/`-wal` у старых снимков (созданные чтением при проверке) остаются рядом
   с копией — безвредны, чистятся при ротации снимка не автоматически.
