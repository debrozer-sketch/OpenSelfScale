## 2. Что появилось в интерфейсе

Меню администратора → «Обслуживание» (sub: «База данных, резервная копия, оборудование»).

Экран: пять строк статусов (метка слева, значение справа, цвет: чёрный — норма,
янтарный — внимание, красный — проблема), кнопка «Обновить», две кнопки действий,
строка «Операция выполняется, подождите…» при BUSY.

Статусы (из реальных данных приложения, сборка в фоновом потоке):
- **База данных:** «доступна · товаров N» / «недоступна» (red) / «ошибка проверки» (red,
  по `integrity_check`).
- **Резервная копия:** «копия от ДД.ММ.ГГГГ ЧЧ:ММ» (файл в каталоге копий — он появляется
  только атомарным rename после проверки снимка) / «резервных копий нет» (янтарный).
- **Весы:** из снимка WeightSource: «подключены · вес готов» / «подключены · вес
  нестабилен» (янтарный) / «отключены» (красный).
- **Принтер:** из `PrinterHealth` демона: «готов» (только если `seen` — демон получал
  ответ принтера), «нет данных» (нейтрально, пока ответов не было), «ошибка» (красный),
  «занят: этикетка в лотке» (янтарный), «кончилась бумага» (красный).
- **Синхронизация:** «нет данных» — приложение не хранит состояние последней синхронизации;
  выдумывать статус нельзя, это честно указано.

Каждая проверка независима: недоступная база не мешает показать весы/принтер/копии.

## 3. Операции

**Создать резервную копию** — реальный `backup::create_backup` (SQLite Backup API,
lock-файл, ротация KEEP=10) в фоновом потоке; `MAINT_BUSY` исключает одновременный
запуск (повторное нажатие игнорируется); на время операции кнопки заблокированы
(`maint-busy`, opacity + disabled); результат — popup «Резервная копия создана: <имя
файла>» или «Не удалось создать резервную копию. Попробуйте ещё раз.» (полный текст
ошибки — в лог); после завершения статусы пересобираются — дата копии обновляется.

**Проверить принтер** — переиспользует существующий механизм: диалог подтверждения
«Будет напечатана тестовая этикетка. Продолжить?» → общий с настройками `PRN_BUSY` →
существующая очередь `PrinterRequest::Test` печатного демона (`print::print_test_label`).
Новых механизмов печати нет. Результат: «Задание отправлено принтеру. Проверьте печать
этикетки.» — сознательно не «напечатана»: ветка Test подтверждает отправку и статус, но
не датчик лотка. Ошибка — popup с кратким текстом, подробности в лог. Автоповторов нет.

**Обновить** — пересборка статусов в фоновом потоке; UI не блокируется.

## 4. Ошибки и BUSY

- Повторный запуск занятой операции: `MAINT_BUSY.swap` (обновление/копия) и `PRN_BUSY`
  (проверка принтера) — игнорируются; кнопки дополнительно disabled на UI.
- BUSY-состояние снимается в том же invoke, что обновляет статусы; паника фонового
  потока снимает BUSY и пишет в лог (catch_unwind).
- Операции выполняются вне UI-потока; результаты доставляются через
  `invoke_from_event_loop`.
- Restore из UI не добавлялся (по требованию).

## 6. Что осталось недоступно и почему

- **Синхронизация**: приложение не хранит время/результат последней синхронизации —
  показывается «нет данных». Добавление хранения — отдельная задача.
- **Restore из UI** — запрещён рамками волны (защищённая CLI-операция).
- **Подтверждение выдачи тестовой этикетки датчиком**: ветка `Test` печатного демона
  не ждёт этикетку в лотке (в отличие от товарной печати) — поэтому результат проверки
  формулируется как «задание отправлено». Усиление ветки Test — отдельная задача.
- **Физический тач** не проверялся (Slint testing-бэкенд); зоны кнопок геометрически
  не пересекаются.

## 7. Возможные следующие улучшения (не начинать без отдельной задачи)

1. Хранить в приложении время и результат последней синхронизации — показать в «Обслуживании».
2. Ждать датчик лотка в ветке `Test` (как в `print_job`) — тогда «Проверить принтер»
   сможет подтвердить фактическую печать.
3. Кнопка «Проверить принтер» вне экрана администратора не нужна — но быстрый доступ к
   статусам весов/принтера уже есть в «Состоянии» (23): при желании объединить.
4. Автоматическое обновление статусов экрана «Обслуживание» по таймеру (сейчас — по кнопке).
