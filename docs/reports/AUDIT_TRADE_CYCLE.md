# Аудит торгового цикла и повторной печати — OpenScale

Дата: 2026-10-31. Версия после исправлений: sha256 `610bd3dc64cd097259d41fe31377860d3473aea47d20f2c4095f08f67ad826de`.

## 1. Фактическая схема торгового цикла

```
[phase 0] витрина
   │ тап по плитке            flow.rs on_plu_tap (45–65)
   │   pending=Some(entry), popup_open=true
   ▼
[popup подтверждения]                 (phase 0)
   │ тик 100 мс рисует живой вес и суммы   tick.rs 102–133
   │ (только ws==2 и port_up, иначе «—»)
   │ ОК: on_plu_confirm (72–108)
   │   ws==2 (свежий стабильный вес) иначе — ранний выход
   │   item перечитывается из БД
   │   print_weight_g = округлённая масса этого же снимка  ← фиксация веса
   │   pending=None, selected=Some, phase=2, popup закрыт
   ▼
[phase 2] покупка зафиксирована, печать
   │ тик: запуск задания, если !tray_blocked && print_at=None  tick.rs 158–183
   │   print_op += 1 (номер операции), spawn потока
   │ print_for_item_with_cancel  print.rs 1560–1640
   │   sum_kop по item.price + rounding из БД (та же формула, что в popup)
   │   print_log_add(ok=0) → rowid        ← ФИКСАЦИЯ ОПЕРАЦИИ (до печати)
   │   очередь в демон (mpsc, последовательно; STALE_JOB 25 с)
   │ демон daemon_loop  print.rs 888–953
   │   печать в порт, контроль «этикетка выдана», отмена до старта
   │   print_log_mark(rowid, ok)          ← пометка исхода
   ▼
[phase 3] этикетка напечатана → DONE_TIMEOUT → reset → [phase 0]
[phase 4] ошибка печати → ERROR_TIMEOUT → reset → [phase 0]

Отказы:
  PRINT_TIMEOUT 30 с → cancel, print_op += 1, phase 4   tick.rs 200–216
  tray_blocked (этикетка не снята / нет бумаги) — печать отложена
```

Единственный источник истины текущего измерения — `WeightSource.inner`
(`weight.rs`), снимок берётся через `snapshot()`. UI и расчёт после исправлений
используют один и тот же снимок: popup показывает массу снимка, confirm
фиксирует массу этого же снимка как вес этикетки; пересчёта в тике больше нет.

## 3. Находки

| ID | Приоритет | Находка | Доказательство | Статус |
|---|---|---|---|---|
| N1 | P0 | Вес фиксировался тиком после подтверждения: между `on_plu_confirm` (ws==2, сумма X) и следующим тиком масса могла смениться на другой стабильный Y — этикетка печаталась с суммой Y | `flow.rs on_plu_confirm` не записывал массу; `tick.rs` пересчитывал `print_weight_g` из нового снимка | Исправлено: масса фиксируется в confirm из того же снимка, тик не пересчитывает |
| N2 | P1 | Операция записывалась в `print_log` после печати: крах процесса между выдачей этикетки и записью терял продажу из отчётов | `print.rs daemon_loop` — `print_log_add` после `print_job` | Исправлено: запись попытки (ok=0, rowid) до передачи на принтер, демон помечает исход; БД недоступна — печать не выполняется |
| N3 | P2 | Idle-сброс оставлял popup открытым с очищенным `pending` — экран без действий до ручного закрытия | `session.reset_state` не трогает UI; popup гасился только в confirm/cancel | Исправлено: popup закрывается при всех idle-сбросах |
| N4 | P2 | Мёртвые переходы phase 1 (`phase=1` достигался только откатом из phase 2, который исчез после N1) | `tick.rs 158–177` (до правки), установка `phase=1` нигде не выполнялась как вход | Исправлено: ветки удалены, добавлена явная ветка запуска печати |
| N5 | P2 | `PRINT_TIMEOUT` отменяет флагом, но демон проверяет cancel только до старта печати — этикетка всё равно выйдет, UI покажет ошибку, журнал получит ok=1, поздний результат пропускается по `print_op` | `tick.rs` cancel; `daemon_loop` проверка до `print_job`; ESC/POS не гарантирует прерывание передачи | Принят протокольный предел; данные операции не теряются и не дублируются |
| N6 | P3 | `meta.name = namefirst` (без `namesecond`) — в журнале печатей имя короче, чем на этикетке | `print.rs print_for_item_with_cancel` | Отложено |
| N7 | P3 | Повторной печати покупок нет; «печать для другой покупки» невозможна: `meta` формируется из `selected`/`print_weight_g` того же снимка, что и фиксация; задание не ретраится автоматически | код `tick.rs`/`print.rs` | Инвариант задокументирован |

Подтверждённые инварианты (проверены по коду):
- двойное подтверждение: `pending=None` после первого, `phase>=2` блокирует тапы, повторный confirm — ранний выход;
- параллельные задания: демон обрабатывает канал последовательно, одно задание не отправляется дважды;
- отрицательная/нулевая масса: `weight_state` → 0, тик откатывает `weight_g<=0` до правки, теперь confirm невозможен при ws!=2;
- переполнение: масса ≤ 99 999 г (`WeightLimit`), суммы в i64 копейках;
- устаревший вес: `apply_staleness` (порт вниз при тишине) + фиксация живости в popup/confirm.

## 4. Сценарии отказов (после исправлений)

| # | Сценарий | Фактическое поведение | Риск |
|---|---|---|---|
| 1 | Вес отключён до подтверждения | confirm при ws!=2 невозможен; на экране `--.---` | нет |
| 2 | Вес отключён сразу после подтверждения | масса уже зафиксирована, печать завершается независимо от состояния весов | нет |
| 3 | Крах при записи | SQLite INSERT атомарен; запись до печати | нет |
| 4 | Крах после записи, до печати | в журнале остаётся ok=0 (виден как ошибка), этикетки нет; повтор — новой покупкой | нет |
| 5 | Крах во время печати | ok=0 остаётся; этикетка может выйти частично/полностью — протокольный предел | редкий расходник |
| 6 | Принтер отключён до передачи | `with_port` не откроется → ok=0 → phase 4 | нет |
| 7 | Принтер отключён в процессе передачи | ошибка записи → ok=0; частичная этикетка возможна | редкий расходник |
| 8 | Быстрые нажатия подтверждения | один confirm проходит, остальные — ранний выход; `print_op` и guard `print_at` исключают повторный запуск | нет |
| 9 | Новая покупка после ошибки | phase 4 → таймаут → 0, состояние очищено; демон свободен | нет |
| 10 | Повторная печать старой этикетки | функции нет; повтор = новая покупка (новая запись) | нет |
| 11 | БД недоступна | печать не выполняется (ошибка), продажа без записи запрещена | нет (отказ в сторону консистентности) |
| 12 | Перезапуск при незавершённой операции | фаза не восстанавливается (в памяти); фиксированная попытка остаётся в журнале ok=0 | виден в отчётах как ошибка |

## 5. Исправления и коммиты

- `datastore`: `print_log_add` возвращает rowid (`Result<i64>`), добавлен `print_log_mark`.
- `print.rs`: журнал попытки до печати (`log_rowid` в `PrinterRequest::Print`), демон помечает исход.
- `flow.rs`: `on_plu_confirm` фиксирует `print_weight_g` из подтверждённого снимка.
- `tick.rs`: запуск печати без пересчёта массы; удалены мёртвые phase-1 переходы; popup закрывается при idle-сбросе.

Коммит: см. `git log` (`fix(trade)`), деплой sha256 `610bd3dc…`, сервис активен.

## 6. Тесты

- `print_log_mark_updates_attempt_outcome` — пометка исхода по rowid, попытки различимы;
- `print_log_attempt_survives_without_mark` — фиксация попытки до печати переживает отсутствие пометки (крах процесса);
- ранее добавлены: актуальность веса в popup, устаревание снимка, сетка отделов.

Итого 177 тестов зелёные; release-сборка Linux без предупреждений.

## 7. Оставшиеся риски и ограничения

- ESC/POS: «байты ушли, подтверждение не получено» может дать этикетку при ok=0 в журнале (и наоборот исключён: ok=1 ставится только по факту выдачи). Автоматических повторов нет — дублирование из приложения исключено.
- Отмена по таймауту не прерывает уже идущую передачу (N5).
- Фаза не восстанавливается после перезапуска — по дизайну киоска (покупка повторяется вручную), фиксированные попытки остаются в журнале.
