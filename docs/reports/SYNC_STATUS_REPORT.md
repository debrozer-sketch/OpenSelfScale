# Отчёт: состояние и результат синхронизации (волна 17)

Дата: 2026-11-01. Последний статус синхронизации хранится в БД и показывается
на экране «Обслуживание».

## 1. Где фиксируются начало и завершение

Три места запуска синхронизации: авто-приём drop-каталога и авто-опрос FTP
(оба — потоки `sync::spawn_auto_sync`), CLI-команда `openscale --sync`
(`main.rs`, `Mode::Sync`). Ручного запуска из UI нет.

- **Начало** — `sync_status::begin(&cfg.db_path)`: одна вставка в `sync::run`
  (после проверки настроек центра) и в `sync::run_drop` (после захвата
  `sync.lock` — то есть только когда приём реально начался; проверки
  `ready.flg` без выгрузки попыткой не считаются). Логика `sync.rs` не
  переписывалась.
- **Завершение** — `sync_status::finish(db_path, ok, …)`: в обоих циклах
  `spawn_auto_sync` (включая ветку паники потока — записывается «прервано
  внутренней ошибкой») и в CLI. Успех фиксируется только после полного
  завершения приёма (включая удаление исходных файлов: отложенное удаление —
  это `Err`, попытка не считается успешной).

## 2. Где и в каком формате хранятся данные

Одна строка таблицы `app_settings` (существующая key/value, никаких
миграций): ключ `sync.last`, значение JSON:

```json
{"a": 1793581200, "s": "ok" | "err" | "run", "u": 1790000000, "e": "причина"}
```

- `a` — время попытки (unix, с), `s` — состояние, `u` — время последнего
  успеха (копируется из предыдущей записи), `e` — краткая причина ошибки.
- Отсутствие записи = «Ещё не выполнялась».
- Запись атомарна (`INSERT OR REPLACE`), история не ведётся.

## 3. Совместимость со старыми БД

Таблица `app_settings` уже есть в схеме (`CREATE TABLE IF NOT EXISTS`) —
старые базы получают её при очередном открытии, новые записи не требуют
изменений схемы. Нет записи — честное «ещё не выполнялась».

## 4. Ошибки и параллельные запуски

- **Ошибка записи статуса** не влияет на результат синхронизации: `begin`/
  `finish` открывают отдельное соединение (`datastore::open`, WAL,
  busy_timeout 5 с), все сбои записи — `log::warn`, результат операции не
  меняется (тест `failed_status_write_does_not_affect_operation`).
- **Гонки**: запись одной строки атомарна; конкурентные завершения (CLI +
  авто) сериализуются SQLite. Дата последнего успеха при ошибке не теряется:
  `finish` читает предыдущую запись и переносит `u` (тест
  `parallel_writes_keep_valid_state` — 4 потока, состояние валидно).
- **Прерванная попытка**: если процесс умер во время приёма, остаётся
  запись `run`. Пока она свежее 15 минут — «Выполняется»; старше — «…—
  прервана» с причиной «приложение завершилось во время приёма» (окно
  покрывает максимальную длительность приёма: таймауты FTP/конвертера 60 с,
  ожидания файлов 60+30 с).
- **BUSY** существующих механизмов не затронут (`MAINT_BUSY`, `NET_APPLYING`,
  `PRN_BUSY`).
- **Скрытые детали**: причина ошибки проходит `sync_status::safe_reason` —
  оператору уходит класс ошибки («выгрузка повреждена…», «сервер центра
  недоступен…», «каталог обмена занят…» и т. п.), без путей, SQL и
  внутреннего текста (тест `safe_reason_hides_paths_and_details`). Полный
  текст остаётся в журнале — существующие `log::error` не менялись.

## 5. Экран «Обслуживание»

Вместо «нет данных» — реальные состояния (строки добавляются динамически):

- без записи: `Синхронизация — Ещё не выполнялась`;
- свежий `run`: `Синхронизация — Выполняется` (янтарная);
- успех: `Последняя попытка: ДД.ММ.ГГГГ ЧЧ:ММ — успешно`;
- ошибка: `Последняя попытка: … — ошибка` (красная) + `Причина: …` (янтарная)
  + при наличии прошлых успешных приёмов `Последний успех: ДД.ММ.ГГГГ ЧЧ:ММ`;
- старый `run`: `…— прервана` + «приложение завершилось во время приёма».

Экран обновляется при входе/кнопке «Обновить» и автоматически после
завершения синхронизации: `tick.rs` получает сообщение от потока приёма и,
если открыт экран 27, запускает `spawn_maint_refresh` (фоновый поток,
`MAINT_BUSY` защищает от двойного обновления).
