# Волна 20.1: устранение четырёх остаточных дефектов wave20

Исправлены только перечисленные дефекты. Без рефакторинга и смены архитектуры.

## 1. B2 — явное владение попыткой синхронизации (токен вместо глобального ATTEMPT)

**Было:** `ATTEMPT: Mutex<Option<i64>>` хранил один глобальный идентификатор.
`finish()` вызывался снаружи `run()`/`run_drop()` (spawn_auto_sync, CLI), а
`sync.lock` освобождался при возврате: в окне между возвратом и finish другая
задача могла вызвать `begin()` и перезаписать ID — первый finish завершал
чужую попытку своим результатом.

**Стано:**
- `sync_status::AttemptToken(i64)` — владение попыткой явно: `begin()` возвращает
  `Option<AttemptToken>`; `finish(db_path, token: Option<AttemptToken>, ok, report, err)`
  завершает запись только если она `run` с тем же id (токен — Copy, завершать
  может другая задача, если это предусмотрено вызывающим кодом).
- Глобальный `ATTEMPT` и `take/store/reset_attempt_id` удалены. Владение
  хранится в самой записи (поле `i`) — токен межпроцессно безопасен.
- `run()` и `run_drop()` вызывают `begin()` после захвата `sync.lock` и
  завершают попытку внутри себя, до выхода из-под блокировки (обёртки
  `run_ftp`/`drop_receive`).
- CLI `--sync` (main.rs) и оба цикла `spawn_auto_sync` (FTP и drop) больше не
  вызывают `finish` сами. При панике потока токен теряется вместе с задачей:
  запись остаётся `run` и после RUNNING_WINDOW показывается как «прервана» —
  это соответствует факту.
- `begin() == None` (БД недоступна, запись не состоялась) — задача продолжает
  синхронизацию без статуса, `finish` для неё не вызывается; отказ из-за
  занятого `sync.lock` не меняет статус; ошибка не затирает дату последнего
  успеха — семантика сохранена.

**Файлы:** `app/openscale/src/sync_status.rs`, `app/openscale/src/sync.rs`,
`app/openscale/src/main.rs`.

**Тесты (реальные сценарии):**
- `stale_token_finishes_nothing_after_newer_begin` — сценарии 1–2: два begin,
  finish A после начала B; запись B остаётся `run` с id B, результат A не записан.
- `own_token_finishes_own_attempt` — сценарий 3: B завершает своим токеном;
  отложенный finish A перезаписи не делает.
- `absent_token_does_not_touch_record` — сценарий 4: finish без токена ничего
  не меняет (в т.ч. завершённую запись).
- `cross_process_foreign_id_cannot_finish` — сценарий 5: запись перезаписана
  «другим процессом» (новый id, как делает begin другого процесса) — finish A
  не завершает чужую запись.
- `parallel_writes_keep_valid_state` — 4 реальных потока begin→finish с
  файловой БД: после гонки статус валиден и завершён.
- `busy_lock_refusal_is_not_recorded_as_error` — отказ из-за занятой
  блокировки (нет токена) не меняет статус выполняющейся попытки.

## 2. D1 — maint_rows действительно вне UI-потока

Проверка всех вызовов `maint_rows()`: экран «Состояние» — `spawn_menu_task`
(фоновый), ручное обновление — `spawn_maint_refresh` (фоновый), тесты — вне UI.

Исправлены два обработчика, где сбор был внутри `invoke_from_event_loop`:
- после резервного копирования: `maint_rows()` собирается в рабочем потоке
  (в catch_unwind; при панике — строка «статус не собран после копии»), затем
  `invoke_from_event_loop` только обновляет UI;
- после тестовой печати: то же.

Гарантированное снятие BUSY: `MAINT_BUSY` снимается в invoke-замыкании; если
event loop недоступен (`invoke` вернул Err) — снимается сразу в рабочем потоке.

**Файл:** `app/openscale/src/settings.rs`.
**Проверка:** три пути (ручное обновление, успешный backup, завершение test
print) покрыты сценарием S18 на стенде — ok.

## 3. C3 — единый статус принтера на обоих экранах

- `maint_rows()`: локальные ветвления по `fault/seen/paper_end/label_waiting`
  удалены — используется `print::status_line(cfg.printer.enabled)`.
- `status_rows()`: локальные ветвления удалены — тот же

**Файл:** `app/openscale/src/settings.rs`.
**Тест:** `printer_status_is_same_on_both_screens` — выключенный принтер
одинаков и не готов; включённый до первого ответа — «нет ответа» на обоих
экранах, не «готов». Полная матрица состояний (молчание → ошибка связи,
авария не маскируется бумагой, near-end/paper-end, готов только при

`paper_states_come_from_l4_bits`, `silence_is_link_error_and_clears_paper_status` —
статус один, следовательно одинаков на обоих экранах.

## 4. A2 — ошибки изоляции sidecar-ов при restore не глушатся

**Было:** после замены main-файла ошибки удаления старых `-wal`/`-shm`
глушились (`let _ =`) — восстановленная база могла открыться с посторонними
sidecar-ами.

**Стано (`backup.rs`):**
- Новый этап `quarantine_sidecars(db_path, pre)`: старые sidecar-ы
  переименовываются в изолятор рядом с pre-копией (`…db-wal.stale`/`…db-shm.stale`)
  ДО замены main. Не удаление, а обратимая изоляция: исходное состояние уже
  гарантированно сохранено (pre создан ранее), а при ошибке изоляции уже
  перемещённые sidecar-ы возвращаются на место.
- Ошибка изоляции прерывает restore до любых изменений main-файла —
  «исходная база и её данные доступны» выполняется тривиально.
- Новая БД не открывается и миграции не запускаются, пока sidecar-ы не
  изолированы (порядок этапов: pre → изоляция → rename → открытие/проверка).
- Ошибки отката не скрываются: существующая ветка проверки БД возвращает
  составную ошибку и пишет в журнал (`log::error`).

**Тесты:**
- `quarantine_wal_blocked_keeps_sidecars` — сценарии 1+3: изолятор -wal занят
  каталогом → Err, оба sidecar-а на месте.
- `quarantine_shm_blocked_rolls_back_wal` — сценарий 2: изолятор -shm занят →
  Err, уже изолированный -wal возвращён компенсацией.
- `quarantine_success_removes_sidecars_from_work_path` — сценарий 4: успех —
  sidecar-ов на рабочем пути нет, изоляторы рядом с pre.
- `restore_fails_when_wal_quarantine_blocked` — интеграция: restore не
  успешен при блокированной изоляции, исходная база цела (открытое
  соединение удерживает sidecar, каталог блокирует rename на обеих ОС).
- `rollback_reports_sidecar_removal_error` — сценарий 5: rollback с
  неустранимой помехой возвращает Err, pre не потерян, исходная база доступна.
- `restore_rollback_restores_wal_state_fully` (волна 20) продолжает проверять
  откат при провале проверки БД.
