# Отчёт: проверяемость UI и сквозные сценарии (волна 7)

Дата: 2026-11-01. Slint 1.9.2. Стенд проверен деплоем sha256 `7cdad600…`, сервис `active`.

## 1. Механизм тестирования

Штатные средства Slint 1.9 (без смены версии и тяжёлых фреймворков):

- крейт `i-slint-backend-testing@=1.9.2` (dev-dependency): testing-бэкенд без физического дисплея;
  `init_integration_test_with_mock_time()` — один раз на процесс;
- `mock_elapsed_time()` — детерминированная прокрутка таймеров (тик 100 мс выполняется синхронно,
  произвольных sleep в тестах нет; единственный реальный интервал — сценарий устаревания снимка,
  где время само является тестируемыми данными);
- нажатия — `invoke_*` реальных коллбэков (`dept_tapped`, `plu_tapped`, `plu_confirm`, `search_open`,
  `key_tapped`, `menu_tap`, `admin_close`, `up`): выполняются настоящие обработчики `flow`/`settings`;
- состояние UI читается сгенерированными `get_*` (`get_screen`, `get_items().row_count()`,
  `get_popup_open/empty`, `get_weight_text`, `get_scales_ok`, `get_status_text`);
- фоновые job'ы (`relayout`/`refresh_data` → `invoke_from_event_loop`) прокачиваются helper'ом
  `pump()` — ровно один оборот event loop, детерминированно.

Ограничение Slint 1.9: `init_integration_test_*` вызывается один раз на процесс → все сценарии
выполняются в одном `#[test]` (`ui_scenarios`, src/ui_tests.rs).

## 2. Структурные изменения (минимальные)

- Крейс переведён на lib+bin (`src/lib.rs`, main.rs — тонкая обёртка): unit-тесты получили доступ
  к композиции приложения; поведение production не изменено.
- `weight.rs`: `#[doc(hidden)] pub fn frozen(snap)` — тестовый источник веса без потока опроса;
  снапшотом управляет тест, тик прокручивает UI.
- `ui_tests.rs`: харнесс `build_app()` повторяет композицию `run_kiosk` (без `ui.run()`, без
  физических демонов): seed БД (2 товара, отдел, привязка группы, wizard done), flow::install,
  settings::install, relayout, tick::start.
- Публичность: `admin::PALETTE_NAMES`, `tiles::stock_palette`, `settings::startup_setup_render`.

## 3. Автоматически проверяемые сценарии (ui_scenarios)

Основные:
1. Старт: отделы загружаются асинхронно, киоск на торговом экране (0/2).
2. Открытие каталога (dept-tapped → экран 2, товары показаны), возврат (up → экран 0).
3. Поиск (search-open, key-tapped): найденные результаты, пустой результат, текст запроса.
4. Вес от тестового источника: `weight_text == "1.350"`, весы на связи.
5. Изменение веса 1.350→2.000: пересчёт суммы в открытой карточке (269.99→399.98 ₽), масса в карточке.
7. Подтверждение: popup закрыт, фаза 2, вес зафиксирован (2000 г), товар выбран.
8. Формирование задания печати: спавн реального потока печати; порт недоступен → ошибка → фаза 4,
   статус «Ошибка печати», `print_at` очищен.
9. Возврат в исходное состояние: фаза 0, выбор очищен.
10. Отчёты: вход администратора, `menu-tap("actionlog")` → экран отчётов, поуровневый `admin_close`
    → возврат в торговый интерфейс, без зависших popup.

Некорректные:
- N1 весы недоступны: `scales_ok=false`, вес «--.---»;
- N2 нулевой вес: popup помечен пустым, подтверждение отклонено (фаза 0); карточка остаётся для
  отмены — в UI кнопка подтверждения заблокирована (`enabled: !popup-empty && weight-state == 2`),
  отмена закрывает;
- N3 устаревший снимок (1,6 с > SNAPSHOT_STALE_MS): весы «недоступны», вес скрыт;
- N4 несуществующий товар: карточка не открывается;
- повторное подтверждение без товара — noop (фаза не меняется);
- ошибка печати — сценарий 8;
- быстрые переходы: triple dept-tapped → стабильно экран 2; double up → экран 0.

## 4. Найденные дефекты и исправления

Дефектов на границе UI и бизнес-логики не обнаружено: блокировки BUSY-состояний, защита
повторных нажатий (`phase >= 2`), очистка веса при выходе из фазы печати, поуровневое закрытие
админ-меню — работают согласно замыслу и закреплены тестами.

Попутно уточнены (зафиксированы как наблюдения, не дефекты):
- `print_op` растёт и на `reset_state` (защита от поздних результатов) — тест проверяет `>= 1`,
  а не абсолютное значение;
- устаревание снимка живёт на реальном времени (`Instant`), mock-время Slint на него не влияет.

## 7. Оставшиеся ограничения

1. Физический EscPos-принтер в тестовом контуре не эмулируется (serialport): позитивный путь печати
   до байтов этикетки покрыт unit-тестами print.rs (без железа), сквозной «от нажатия до бумаг» — нет.
2. Тарирование: UI-кнопка ставит флаг источника веса; физика драйвера покрыта unit-тестом
   (fake_scales_zero_request_reaches_driver); сквозной путь без железа не проверяется.
3. Тест использует `invoke_*` коллбэков; клики через `ElementHandle` (координаты TouchArea)
   требуют `SLINT_EMIT_DEBUG_INFO=1` на этапе компиляции UI — оставлено на случай потребности.
4. Анимации переходов Slint под mock-временем не проверяются (наглядность вне объёма волны).
