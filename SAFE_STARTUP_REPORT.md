# Отчёт: безопасный запуск и режим обслуживания (волна 9)

Дата: 2026-11-01. Стенд: Debian, systemd-юнит `openscale-kiosk` (пользователь `administrator`),
БД `/home/scales/plu.db` (WAL, 218 товаров).

## 1. Безопасный запуск при ошибке БД (fail-closed)

Различаются три ситуации (новый `backup::probe_startup`):

| Ситуация | Признак | Поведение |
|---|---|---|
| Первичная установка | нет файла БД и нет маркера `plu.db.installed` | штатный путь: мастер настройки, БД создаётся |
| БД потеряна после установки | нет файла БД, маркер есть | экран недоступности |
| БД повреждена/не обслуживается | файл есть, но `integrity_check` не «ok», либо открытие/миграции/`load_all` падают | экран недоступности |

Экран недоступности (`db-unavailable`, оверлей в main.slint):
- полноэкранная заглушка «БАЗА ДАННЫХ НЕДОСТУПНА. Торговля приостановлена. Обратитесь
  к администратору.» + указатель на журнал; перехватывает все касания (TouchArea);
- в логе — точная техническая причина и две команды: `openscale --db-check` и
  `systemctl stop openscale-kiosk && openscale --restore <снимок>`;
- торговые операции запрещены дважды: визуально (оверлей) и в логике — `db_unavailable`
  в `Kiosk` блокирует `plu-tapped`, `plu-confirm`, `dept-tapped`, `search-open`,
  `key-tapped` (src/flow.rs); подтверждение/печать невозможны;
- не создаются: новая пустая БД, задания печати; не запускаются авто-синхронизация
  и демон печати (им нужен доступ к БД); релайаут каталога не выполняется;
- весы и экран работают (оператор видит сообщение, а не чёрный экран).

Проверено на стенде: повреждённый файл БД (`garbage`) → сервис `active`, киоск не торгует,
в логе причина и инструкции. После возврата исправной БД и `systemctl restart` — нормальная
торговля. Существующая БД никогда не перезаписывается пустой; `--db-check` на месте.

## 2. Межпроцессная блокировка обслуживания (flock)

`backup::MaintLock` — штатный Linux `flock` (LOCK_SH/LOCK_EX | LOCK_NB) на файл
`<БД>.lock`:

- работающий киоск держит **shared**-блокировку всё время работы с БД (с получением
  до probe; недоступен — до замены файла);
- `--restore` первым же действием берёт **exclusive**; занято — отказ без единого
  изменения файла (проверено: `flock -x … sleep` в фоне → `--restore` отклонён,
  БД цела);
- повторный запуск сервиса во время восстановления: новый киоск ждёт shared-блокировку
  (15 попыток × 2 с); не дождался — выход, systemd повторит; доступ к заменяемой БД
  не получается никогда;
- освобождение — ядром при закрытии fd: штатный выход, `kill -9`, крах (проверено:
  после `kill -9` оба процесса мертвы, `--restore` выполняется сразу);
- защита работает между процессами и не зависит от PID-файлов и `systemctl is-active`
  (тот и comm-скан оставлены только как понятное сообщение об ошибке).

Дополнительно исправлен дефект волны 8, вскрытый fail-closed на стенде: файлы,
создаваемые CLI обслуживания через sudo, получали владельца root:root 0600 и были
недоступны киоску. Теперь восстановленный файл БД, файл блокировки, маркер и каталог
снимков наследуют владельца каталога БД (сервисного пользователя) —
`backup::match_owner_to`.

## 3. Порядок запуска и восстановления

Запуск: создать каталог БД → shared-flock (retry 30 с; занято — exit, systemd повторит)
→ `probe_startup` (маркер/integrity/миграции/чтение) → Ready/FirstInstall: обычный старт
(маркер пишется) | Unavailable: сброс shared-блокировки, оверлей, торговля запрещена.

Восстановление: exclusive-flock (занято — отказ) → comm-скан живого киоска → проверка
снимка (integrity + схема) → сохранение текущей БД как `pre-restore-*` → атомарная
замена (tmp в той же ФС → rename) → удаление старых WAL/SHM → наследование владельца
→ открытие с миграциями и `load_all`; при неудаче — возврат исходной базы, ошибка.

## 4. Автотесты (cargo test --workspace: 214 passed)

- первичная установка без БД проходит probe (`FirstInstall`);
- БД удалена при живом маркере → `Unavailable`, пустая БД не создаётся;
- мусор вместо БД → `Unavailable`;
- валидный SQLite без обязательных колонок (ошибка загрузки/миграции) → `Unavailable`;
- исправная БД → `Ready`, маркер записан;
- flock: второй EX и SH при активном EX отклоняются; SH при активном SH сосуществует;
  после drop — доступен (unix);
- `--restore` при занятом exclusive — отказ без изменения БД (unix).

UI-сценарий S11 (ui_scenarios): при `db_unavailable` каталог/карточка/поиск не
открываются, подтверждение и печать не выполняются; после снятия флага торговля
работает.

## 5. Проверки на стенде (sha256 свежего бинарника, все команды — sudo)

- штатный запуск: active, каталог отрисован, `plu.db.installed` создан;
- повреждённая БД → active, торговля заблокирована, в логе причина и инструкции;
- `--restore` при работающем киоске → отказ (перечислены pid);
- `kill -9` → flock освобождён, `--restore` выполнен (владелец administrator:scales
  наследован), `--db-check`: integrity ok, 218 товаров, запуск → active, каталог на месте;
- два параллельных восстановления: второе отклонено flock-ом (`flock -x` держатель),
  файлы не изменены; после освобождения — восстановление и запуск успешны.

## 6. Ограничения

1. Межпроцессные flock-тесты в Rust — только unix; на Windows-разработке блокировка
   заглушка (кросс-процессная семантика подтверждена на стенде).
2. Ручной `--sync` при потерянной БД создаст пустую (datastore::open) — выполняйте его
   только после восстановления; в киоске авто-синхронизация при недоступности отключена.
3. В режиме недоступности администраторское меню UI недоступно (оверлей); обслуживание —
   через SSH (`--db-check`, `--restore`).
4. Уведомление оператора — текст на экране; звук/мигание не предусмотрены.
