# Ворох проблем весов (реестр) — что НЕ повторять в новом ПО

Дополнение к `AUDIT.md`. Формат: проблема → корневая причина (если найдена) →
требование к новому ПО. Разделы сгруппированы по слоям.

## А. Печать этикеток

**А1. Этикетка выходит не полностью.**
Корневая причина (по конфигу и коду): печать в page mode с абсолютными
координатами, а параметры подачи подобраны вручную «на глаз»: `backwardSpace=75`
(откат этикетки после печати), `optoThermoSpace=362` (расстояние между
оптоэлектронным датчиком зазора и термоголовкой), `additionalLabelFeed=0`.
При смене партии этикеток или износе датчика математика съезжает — хвост
остаётся в принтере.
→ Требование: калибровка подачи из GUI с живым тест-принтом; автоподбор зазора
(прогон N этикеток с измерением); хранение калибровки per-принтер в БД, не в
конфиге руками.

**А2. Этикетка вышла, и следом уходит ещё одна (двойная подача).**
Корневая причина: `disableStatusCheck=1` — приложение не читает статусы
принтера (real-time status transmission в коде есть, но отключено), датчики
зазора опрашиваются только через checkLabelState в момент взятия этикетки;
двойная подача = ложное срабатывание датчика зазора при подаче.
→ Требование: статус-мониторинг принтера всегда включён (бумага, зазор, ошибка);
событийная логика «этикетка снята → готов к следующей»; при двойной подаче —
автооткат и перезапечатка, а не молчаливый брак.

**А3. Настройки печати неинформативны.**
Корневая причина: все параметры — числа в `SelfServiceScales.conf` без единиц,
документации и предпросмотра; эффект виден только после печати брака; часть
настроек вообще только через терминал индикатора (команды вида OB/OA).
→ Требование: экран «Настройка печати» с подписями («откат, точек», «зазор
датчик–голова, точек»), валидацией диапазонов, WYSIWYG-предпросмотром этикетки
(по label.xml координатам) и кнопкой «Тест-печать». Ноль настроек через терминал.

## Б. Данные товаров и конвейер

**Б1. «Весы не реагируют на товар».**
Корневая причина: зашифрованная SQLite (.plu, SQLITECIPHER) расходится с
`plu.xml` (сбой импорта/ALTER TABLE), лечится ручной процедурой `reg_item.ps1`
(снос базы → пересоздание пустой → переимпорт).
→ Требование: обычная SQLite без шифрования; идемпотентный импорт с отчётом
«принято/отклонено/почему»; товар без цены или без записи — явная ошибка на
экране конфигурации, а не молчание на кассе.

**Б2. Гонки в доставке данных.**
Корневая причина: флаги `uploading.flg`/`ready.flg` создаются не всеми
участниками (в sync.x их нет вовсе), `ready.flg` в reg_item.ps1 ставится ДО
заливки plu.xml с паузой 2 с; rsync без рекурсии.
→ Требование: атомарная доставка (один файл-манифест с версией/хэшем, загрузка
во временную папку, переименование после полной проверки); никакого флагового
протокола.

**Б3. Задержка до 30 минут и ручные перезапуски.**
Корневая причина: cron-лftp-зеркало; при сбое оператор руками гоняет
`syncstart.sh`/`sync.x` (вся bash_history на это указывает).
→ Требование: push-модель (центр инициирует выгрузку по HTTPS/SFTP/MQTT),
применение за секунды; статус «последняя синхронизация» в GUI весов и в центре.

**Б4. Молчаливые отказы импорта.**
Корневая причина: ошибки импорта — WARNING в локальный лог; картинок не хватает
(2450 в img/, при этом в layout.xml есть PLU без файлов → «Cannot open» в логе,
на кнопке default.png).
→ Требование: сводка импорта в центре («на этой весы 12 товаров без картинок»);
проверка целостности набора картинок при выгрузке.

**Б5. Дублирование форматов картинок (bmp 378x378 + jpg), источник правды
размыт (центральный FTP + прямой FTP на весы).**
→ Требование: один формат, одна точка доставки, версионирование контента.

## В. Эксплуатация и стабильность

**В1. Лог без ротации дорос до 7.44 ГБ на диске 25 ГБ.**
→ Требование: ротация из коробки (logrotate/systemd-journald), лимит размера,
метрики диска в GUI.

**В2. Перезапуск через `while true` вокруг приложения + startx из rc.local.**
Корневая причина: падения маскируются бесконечным рестартом (в логе — серии
стартов подряд), нет супервизии с диагностикой.
→ Требование: systemd-unit с рестартом, алертом и журналом причин; никакого
startx из rc.local.

**В3. Оффлайн-диагностика затруднена**: минимальная система (нет strings/nm/
curl), ptrace закрыт, root-доступ только по паролю.
→ Требование: в новом образе — встроенный режим диагностики (сбор состояния
одной кнопкой: версии, порты, счётчики ошибок, дамп последних N строк) и
SSH-ключи вместо паролей.

**В4. Мониторинга нет вообще** — о проблемах узнают по жалобам покупателей.
(PRTG-хук в reg_item.ps1 — единственный намёк на мониторинг, и тот про выгрузку.)
→ Требование: heartbeat весов в центр (вес, принтер, диск, синк, ошибки портов),
панель статуса парка весов.

**В5. Часы/сроки годности**: timesyncd указывает наружные NTP, а весы офлайн —
если время уплывёт, сроки годности на этикетках будут неверными.
→ Требование: NTP от центрального сервера/шлюза; контроль рассинхрона в GUI.

## Г. Безопасность (сейчас — открытый распахнутый сарай)

- FTP с записью и глобальным доступом (vsftpd, порт 21, креды `pos:REMOVED` в
  открытом виде в sync.x);
- VNC-пароль в открытом виде в `.xsessionrc` (порт 5900);
- пароль администратора зашит в `reg_item.ps1`, sudo-пароль — в инструкции на FTP;
- Ubuntu 16.04 EOL без обновлений, репозитории недоступны (весы офлайн).
→ Требование: только SSH с ключами; выгрузка по SFTP/HTTPS с токеном на весы;
VNC убрать или за SSH-туннелем; сервисы не слушать «на всех интерфейсах».

## Сводное требование к новому ПО (выжимка)

1. Два serial-канала (весы Штрих-М 115200, принтер ESC/POS 19200) + полный
   статус-мониторинг принтера и весов.
2. Калибровка печати и WYSIWYG-редактор этикетки вместо магических чисел.
3. Один XML-источник (plu.xml/layout.xml совместимы со старым), атомарный
   push-импорт с отчётом.
4. Обычная SQLite, никаких шифрованных баз и reg-процедур.
5. Ротация логов, systemd-супервизия, heartbeat, NTP от центра.
6. SSH-ключи, SFTP/HTTPS, никакого FTP/VNC-пароля в открытую.
7. Режим диагностики одной кнопкой для «кондовой» поддержки.
