## 3. Весовая часть и периферия — протоколы

### Весы: Штрих-М Слим (ShtrihSlim)
Класс `ShtrihSlim` в бинарнике — драйвер протокола Штрих-М:
- Порт: **`/dev/scales`** (USB CDC от платы NXP; плата сама оцифровывает тензодатчик
  и отдаёт вес по протоколу Штрих-М — тензодатчик «напрямую» трогать не нужно).
- Обмен: LRC-контрольная сумма (`ShtrihSlim::lrc(QByteArray)`), NAK-хендшейк
  («NAK expected but not NAK received») — стандартный протокол весов Штрих-М.
- API: `getScalesStatus(ScalesState*)`, `updateWeight` → `weightChanged(QVariant)`,
  `setZero`, `startMonitoring`, `finishShtrih`, `criticalError`.
- Ошибки в логе: `Scales port error: 0` — регулярно при старте.

### Принтер этикеток: ESC/POS
Класс `Printer` — полный ESC/POS для этикеточного принтера:
- Порт: **`/dev/ttyS3`** (RS-232; `SelfServiceScales.conf`: `port=/dev/ttyS3`,
  `backwardSpace=75`, `optoThermoSpace=362`, `disableStatusCheck=1`,
  `additionalLabelFeed=0`, `labelFormat=1`).
- Page mode, абсолютное позиционирование, `printBarcode`, `selectBarcodeHeight`,
  HRI-шрифты, code page, `setWhiteBlackMode`, зазор датчиков этикетки,
  `sendBackwardSpace` (откат этикетки), статусы `labelIsPrinted`/`labelIsTakenOff`
  (опрос датчиков через `checkLabelState`).
- `loadLogos` — логотипы в память принтера, `testPrint`.
- Бренд вероятно MapleTouch (центральная папка синхронизации называется
  `MappleTouch`) — уточнить по шильдику.

**Вывод:** оба протокола известны и документируемы (Штрих-М: serial, LRC, NAK;
ESC/POS). Реализуемы на любой ОС — Debian (tty) и Windows (COM). Драйверный слой
нового ПО = два последовательных порта.

## 4. Приложение `SelfServiceScales`

- `/home/administrator/sss/SelfServiceScales`, ELF x86-64, Qt5+QML
  (Gui/Qml/Network/Xml/SerialPort/Sql), собран дек. 2017, **не стрипнут**.
- Версия из лога: `v.2.0.2.65.48dd52d`.
- Ресурсы QML зашиты в бинарник (qrc, в т.ч. `ImageButton.qml`).
- Лог `/home/administrator/sss/SelfServiceScales.log` — **7.44 ГБ без ротации**
  (риск заполнения диска). В логе циклические «Cannot open img/<PLU>.jpg» —
  из 2450 файлов картинок в `img/` часть отстала.
- Локальная копия: `audit/artifacts/SelfServiceScales` (271 КБ) — для
  дизассемблирования/строкования на мощной машине.

### Данные товаров
- **`SelfServiceScales.plu`** (200 КБ) — зашифрованная SQLite: в бинарнике
  `QSqlDatabase::setPassword`, таблица `plucodes(plu, price, actionprice,
  itemcode, groupcode, namefirst, namesecond, description, shelflife)`.
- **`plu.xml`** — открытая зеркальная выгрузка: `plunumber, price (в копейках:
  44999 = 449.99), itemcode, namefirst, namesecond, groupcode, shelflife`.
  Новый софт может принимать именно этот формат без расшифровки .plu.
- **`layout.xml`** — дерево кнопок тач-интерфейса: `<group name="Фрукты">` →
  `<button name="ЯБЛОКИ ГАЛА КГ" PLU="2885517" img="2885517.jpg"/>`. Группы,
  порядок и подписи кнопок полностью декларативны.

### Визуал этикетки: `label.xml`
Декларативный шаблон печати (копия в `audit/artifacts/label.xml`):
- `<label width="480">` — ширина этикетки в точках печати.
- `<field x y font size name=...>` — плейсхолдеры: `namefirst`, `namesecond`,
  `description`, `date`, `time`, `shelflife`, `weight`, `price`, `sum`,
  `actionprice`, `actionsum`.
- `<statictext x y font size text=...>` — статические надписи (продавец,
  реквизиты, «По акции»).
- `<barcode x y height>` — штрихкод.
- Атрибуты `action`/`noaction` — переключение зон обычной/акционной цены.
- Схема простая: визуальный редактор нового ПО может читать и генерировать такой
  же XML (или расширить схему), рендер — ESC/POS page mode с абсолютными
  координатами. WYSIWYG-редактор этикетки = прямое развитие этой схемы.

### Синхронизация с центральным сервером
- `/sync/syncfiles/sync.x` (lftp): `open ftp://pos:REMOVED@192.168.0.87`,
  `mirror MappleTouch/` — данные тянутся с FTP центрального сервера.
- `syncstart.sh` (cron каждые 30 мин, ставится settings.sh): rsync в
  `/var/ftp/scale/` + маркер `ready.flg`; приложение подхватывает.
- Картинки товаров: `<PLU>.bmp` (в /var/ftp/scale) и `<PLU>.jpg` (в sss/img).
- Инструкция — `/var/ftp/scalesettings/Инструкция.txt` (содержит пароль sudo —
  в этот документ не перенесён намеренно).

### Конвейер данных: как товары и картинки попадают в весы
Полная цепочка (восстановлена из скриптов, crontab, меток времени и символов
класса `DataUpdater` в бинарнике):

1. **Источник один** — центральный сервер `192.168.0.87`, каталог `MappleTouch/`
   (FTP, креды `pos:REMOVED` в открытом виде). В нём: `plu.xml` (товары, цены в
   копейках, сроки), `layout.xml` (кнопки/группы тач-экрана), `<PLU>.jpg`
   (картинки товаров для экрана), `<код>.bmp` (27 файлов 378x378 8-бит —
   картинки старого формата, вероятно для этикеток/логотипов), копия бинарника.
2. **Транспорт**: root-crontab весов каждые 30 минут: `lftp mirror
   MappleTouch/` в `/sync/MappleTouch/` → `rsync -d` в `/var/ftp/scale/` →
   `echo '' >> /var/ftp/scale/ready.flg`.
3. **Приём на весах**: класс `DataUpdater` внутри приложения
   (`startUpdateMonitoring`) мониторит `/var/ftp/scale/`: реагирует на флаги
   `uploading.flg` / `ready.flg` (строка в бинарнике: «Found uploading.flg...
   Trying to reload data...»), затем:
   - `getPLUDataFromXML(plu.xml)` → `INSERT OR REPLACE INTO plucodes` в
     зашифрованную SQLite `.plu`;
   - `layout.xml` копируется в `sss/` (замечено: метка 09:38, обновляется);
   - `copyImageFiles()` — `*.jpg` → `sss/img/`;
   - флаг снимается (в момент аудита `ready.flg` отсутствует — приложение
     его поглотило; метки `sss/plu.xml`, `sss/img`, `.plu` = 10:00:13,
     через 13 секунд после rsync).
4. **Отображение**: тач-экран строится из `layout.xml` (группы → кнопки
   `name`/`PLU`/`img`), картинка кнопки — `sss/img/<PLU>.jpg`, при отсутствии —
   `images/default.png` (fallback в QML).
5. **Шаблон этикетки** `label.xml` НЕ синхронизируется (лежит с 2017-12-28,
   в `/var/ftp/scale` его нет) — правится локально/вручную.
6. **Альтернативный канал**: vsftpd на самой весы (порт 21, локальный
   пользователь `scale`, chroot `/var/ftp`, запись разрешена) — прямая FTP-заливка
   в `/var/ftp/scale/`, минуя центральный сервер.

### Почему это «неудобно, нестабильно и привередливо» (диагноз)
- Нет транзакционности: rsync без `-r`, флаги `uploading.flg`/`ready.flg`
  создаются не всеми участниками цепочки (в sync.x их нет вовсе) — гонки
  при недоливке.
- Задержка до 30 минут (cron) + ручные перезапуски (`syncstart.sh`, `sync.x`)
  в истории операторов.
- Молчаливые отказы: нет отчётов об ошибках импорта; отставшие картинки —
  просто WARNING в 7-гигабайтном логе.
- Развёртывание канала — ручной `settings.sh` через SSH на каждой машине.
- FTP-креды в открытом виде в двух местах (sync.x на весах, сервер).
- Картинки рассинхронизированы: 2450 в `img/`, часть PLU без картинок.

### Ручной ремонт: `reg_item.ps1` + `reg` (локальный инструментарий)
Скрипт `reg_item.ps1` (применяется, «когда весы не реагируют на товар») через
Posh-SSH делает на весах:
1. `rm /home/administrator/sss/SelfServiceScales.plu` — сносит зашифрованную БД;
2. заливает `reg` (62 КБ, Qt-утилита, драйвер **SQLITECIPHER**), запускает —
   тот создаёт **пустую** зашифрованную базу `plucodes(plu, price, itemcode,
   groupcode, namefirst, namesecond)` в домашнем каталоге; затем она
   перемещается в `sss/`;
3. `shred -u reg` — удаляет утилиту;
4. заливает `layout.xml` и `plu.xml` в `/var/ftp/scale/`, после каждого —
   `touch ready.flg` (принудительный импорт через DataUpdater).

То есть «не реагирует на товар» = расхождение/повреждение зашифрованной `.plu`
(например, падение ALTER TABLE доп. колонок или сбой импорта), и лечение —
пересоздание базы с нуля + переимпорт. Сами симптомы лечатся, причина — нет.

Слабые места процедуры: пароль администратора зашит в скрипт; `reg` читает
ничего и создаёт пустую базу (источник правды — только переимпорт plu.xml);
`ready.flg` ставится ДО заливки plu.xml с паузой 2 с — если DataUpdater успеет
импортировать раньше, уйдёт старый прайс (гонка); регламент ручной, на каждую
машину отдельно. В новом ПО вся эта процедура не нужна: обычная (нешифрованная)
БД, единый источник, идемпотентный импорт, отчёт об ошибках в GUI.

### Автозапуск (цепочка)
1. `/etc/rc.local` → `su - administrator -c startx &`
2. `~/.xsessionrc`: `xset s off`, `xset -dpms` → `x11vnc -forever -bg` → `sh ~/start.sh`
3. `~/start.sh`: `cd sss; while [ 1 ]; do ./SelfServiceScales; done`
4. Артефакт прошлой эпохи: `/home/administrator/scales.conf` (upstart-скрипт,
   systemd не читает, внутри опечатка `end srcript`) — игнорировать.

## 5. Рабочий процесс настройки сейчас (что заменяем)

1. Настройки/данные готовятся централизованно, кладутся на FTP 192.168.0.87.
2. На каждую весы заливается папка `scalesettings` по FTP (vsftpd, порт 21).
3. Оператор по SSH: `sudo chmod +x settings.sh && sudo bash settings.sh`, ответ y —
   скрипт ставит lftp, прописывает cron на 30 мин, запускает синхронизацию,
   удаляет следы.
4. Настройка весового модуля — вручную через терминал индикатора (в истории
   команд вида `OB`, `OA`, цифровые последовательности).
5. Разработка/QA через x11vnc (порт 5900).

Всё это заменяется одним приложением с GUI-конфигурацией по сети: SSH/SFTP
вместо FTP, товары/кнопки/этикетки правятся визуально, централизованно.

## 6. Выводы для нового ПО

1. **ОС**: рекомендую Debian 13 «Trixie» (релиз 2025-08-09, ядро 6.12 LTS,
   безопасность до ~2030 c LTS). Проверено на конкретном боксе: UEFI 64-битный
   (grubx64/shimx64 в ESP) — типовая проблема Bay Trail с 32-битным UEFI сюда
   не относится. 4 ГБ RAM достаточно, SSD 30 ГБ с запасом, вся периферия —
   стандартные USB HID/CDC и serial, обслуживаются ядром 6.12 без
   проприетарных драйверов. Kiosk-режим: cage/labwc (single-app Wayland) или
   X11 как сейчас. Windows-путь закрыт: обычная Win10 EOL 14.10.2025,
   Win10 IoT LTSC 2021 — только security до 2032 через volume licensing и
   устаревшие драйверы GPU Bay Trail, Win11 требует CPU с 8-го поколения —
   J1900 не поддерживается. Ubuntu 24.04 LTS — рабочий запасной вариант
   (kiosk-гайды есть), но тяжелее (snap) и короче поддержка, чем Debian LTS.
2. **Тензодатчик**: читается готовым протоколом Штрих-М с платы NXP через
   `/dev/scales` (вес, статусы, обнуление). Переоснащение железа не требуется.
3. **Печать**: ESC/POS этикетный принтер на ttyS3; шаблон этикетки — XML.
   Визуальный редактор (WYSIWYG поверх той же координатной схемы) → генерация
   ESC/POS. Обратная совместимость с текущими label.xml сохраняется.
4. **Товары**: plu.xml человекочитаем; синхронизация переезжает с FTP+cron на
   HTTPS/SFTP с push-моделью (или MQTT/вебсокет для мгновенного применения).
5. **Тачскрин/графика**: работают из ядра — на Debian идентично.
