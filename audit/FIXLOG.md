## 19.10 — отладка сторожа на стенде

- Симптом: киоск перезапускался каждые ~33 с после включения WatchdogSec=30.
- Причина 1 (наша): сервис с WatchdogSec активировали раньше нового бинарника
  — шторм с раунд-3 бинарником без пингов; install при деплое пропустили.
- Причина 2 (архитектурная, главная): PAM-сессия (PAMName=login) переносит
  процессы киоска из cgroup сервиса в session-XX.scope; systemd
  атрибутирует sd_notify дейтаграмму scope-юниту и игнорирует WATCHDOG=1
  («Got notification message from unexpected unit type») — подтверждено
  debug-логом PID1. NotifyAccess=all не помогает: дело в типе юнита
  отправителя, а не в правах.
- Причина 3: watchdog убивает только xinit; kiosk/Xorg переезжают в
  сессионный scope и переживают рестарт — держат дисплей и порты, новые
  киоски умирают молча (лог замирал на старой сессии). Лечится чисткой
  сирот в start.sh (pkill перед xinit).
- Решение: sd_notify убраны совсем; WatchdogSec/NotifyAccess сняты с юнита.
  Внутренний сторож (watchdog.rs): beat() из UI-тика ставит монотонную
  метку, поток-надзиратель при молчании UI >25 с делает abort —
  systemd Restart=always поднимает киоск. Пригодно и без PAM-нюансов.
- Стенд: после 07:46 ни одного падения за >2 мин (ранее цикл 33 с),
  дерево процессов чистое, бинарник раунда 4.

## 19.10 — стенд: живая калибровка аварий принтера (шаг 3 чеклиста)

Сценарий: отщёлкнута термоголовка → печать → снята лента → печать →
заправка → перезапуск питания принтера.

Новые факты (дополняют PROTOCOL.md §2):

- **Отщёлкнутая термоголовка аварии НЕ поднимает**: двигатель крутит
  ленту, L4 остаётся 0x7E, принтер молча принимает задание, этикетка
  не выходит. Ошибка видна только по отсутствию выдачи (трасса вся
  из 0x7E, выдана=false).
- **Снятая лента при печати → L4 = 0x72** («подача без ленты», как и
  было калибровано).
- **После снятия ленты при ошибке и возврата ленты L4 = 0x12** — новое
  состояние: bit2 и bit3 сняты, лоток-биты сняты. DLE ENQ 1/2 и ESC @
  НЕ снимают; снимается только перезапуском питания принтера. Это
  клин ошибки, а не «подача без ленты» — различать по комбинации битов.
- Автовосстановление из фонового опроса работает: лестница запускается
  сама (кулдаун 10 с), лог «восстановление DLE ENQ 1 → L4 = …».
- Печать без выдачи за 6 с теперь считается ошибкой покупателя
  («этикетка не выдана»), а не успехом.
- Перезапуск питания принтера потянул за собой перезагрузку весов
  (общее питание?) — на стенде; при тираже проверить раздельное питание.
- После перезапуска принтера и перезагрузки весов: L4 = 0x1E (этикетка
  в лотке у датчика снятия), fault снят, экран показывает «уберите
  этикетку» — детект лотка и снятие аварии подтвердились вживую.

### Спайк датчика зазора VKP80II (19.10, --label-probe)

Итерация 1: DLE EOT 1..4 при шаговой подаче (ESC J 1) сквозь зазор —
байты статичны (0x00/0x12/0x12/0x7E), уровни 5..8 не отвечают.
Итерация 2: ESC v=0x00, GS r=0x03/0x00, DLE DC4 — без ответа, ASB (GS a)
не поддержан (в потоке нет байтов). Итог: датчик зазора через команды
статуса недоступен.
Замер времени FF (подача до начала следующей этикетки): 1317/1319/1320 мс
— разброс ±3 мс на трёх повторах. Принято решение: длина этикетки
определяется временем подачи FF (time = offset + k*length); калибровка —
на стенде по двум рулонам известной длины, параметры
[printer] ff_offset_ms / ff_ms_per_mm. Спека обновлена.
Уроки: проба принтера требует остановки сервиса (эксклюзивный лок порта)
— экран весов тёмный на время пробы; длительные SSH-команды — только
через nohup + файл результата (таймаут канала paramiko).

## 19.10.2026 — правки по второму ревью аудита

### Средние (все исправлены)
- **relayout**: после route_unmapped_groups список отделов перечитывается
  из БД — новый «ПРОЧЕЕ» появляется сразу, без пересборки (regression
  от исходного кода ревьюера).
- **print_log**: запись журнала перенесена ПОСЛЕ finish(ack) — открытие
  БД и вставка больше не задерживают ответ покупателю. Добавлены индекс
  idx_print_log_ts и чистка записей старше 90 дней (при старте демона и
  раз в 6 часов).
- **Отчёт**: «Операций за период» — реальный COUNT с теми же фильтрами
  (print_log_count_filtered), а не rows.len() при LIMIT 20.
- **Округление**: комментарий исправлен (арифметическое к ближайшему
  шагу: 26993→26990 вниз). В документации round_sum зафиксировано:
  штрих-код несёт вес, касса пересчитывает сумму сама — режимы 1/2
  включать только после согласования логики с кассовым ПО.
- **Импорт конфигурации**: лимит файла 256 КБ (каталог доступен по FTP);
  применение в одной транзакции (unchecked_transaction + commit); лимит
  отделов 64 и названий 24 символа; клампы idle_timeout_secs сведены к
  10–60 везде (в живом значении импорта было 10–600 — рассинхрон).
- **run_external**: временный файл создаётся в каталоге обмена рядом с
  входным (не в общем /tmp) с create_new (симлинк-атаки исключены);
  stderr в null (пайп не читался — конвертер зависал бы в переполнении);
  лимит вывода 32 МБ; правило «>10% битых записей — файл отвергнут» как
  у plu.xml; external_input проверяется на «просто имя файла».
- **watchdog**: первый beat пишет max(1) мс — ноль зарезервирован под
  «UI ещё не тикнул»; зависший сразу после первого тика UI ловится.

### Низкие и замечания
- **present_wait** вынесен в конфиг [printer] present_wait_secs (дефолт 3,
  потолок 20 с — STALE_JOB 25 с).
- **Лестница восстановления**: после 3 неудач подряд прекращается, попап
  показывает «Выключите и включите питание принтера» (printer-power-hint,
  PrinterHealth.power_cycle_hint); сброс — при выходе принтера из аварии.
  Стенд: клин 0x12 программно не снимается.
- **Минимальный вес**: шаг 5 г убран (10/20/50), клампы 1..1000 → 10..1000:
  шум пустой платформы −6 г, Min торговых весов выше.
- **rust-toolchain.toml**: закреплён stable (минимум 1.89 — edition 2024
  в Cargo.lock). busy_timeout(5 с) задан явно при каждом открытии БД.
- **deploy/vnc_passwd**: в git не входил, добавлен в .gitignore и не
  попадает в архивы аудита; сервис читает пароль из домашнего каталога
  устройства.
- **PROTOCOL.md** дополнен данными стенда: открытая головка без аварии,
  клин 0x12 только питанием, связанное питание принтера и весов,
  недоступность датчика зазора.

## 20.10.2026 — серия 10 печатей с трассой L4 (проблема №1)
