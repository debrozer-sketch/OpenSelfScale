# Протоколы весов 172.32.0.5 — живой дамп (strace)

Источник: `/tmp/scales_io.trace` с работающего приложения, снят strace-ом
во время 3 взвешиваний с печатью. Локальная копия: `audit/artifacts/scales_io.trace`.
Оба порта открыты одним процессом (fd 11 = /dev/ttyACM0=/dev/scales,
fd 13 = /dev/ttyS3 = принтер).

## 1. Весы: Штрих-М, `/dev/scales`, 115200 8N1

### Цикл опроса (безостановочный, ~каждые 0.5–1 с)
```
→ STX '5' ':' '0' '0' '3' '0' LRC        = \x02\x05:0030<   (8 байт)
← ACK                                     = \x06            (может прийти
← STX ... данные ... LRC                    отдельно, приложение дожидается)
→ ACK                                     = \x06
```

### Кадр ответа (14 байт от STX до LRC; подтверждено живым замером на Debian 13)
```
\x02 \x0b ':' \x00 <status> \x00 <масса:4 байта LE32, знаковая> \x00 \x00 \x00 <LRC>
```
Управляемые байты ACK/NAK приходят ПЕРЕД кадром по одному (могут прийти
отдельными чтениями) и в кадр не входят. NAK (\x15) наблюдается на первый
опрос после открытия порта. После приёма кадра host шлёт ACK (\x06).

- `\x0b` — длина payload (11 байтов после него, LRC вне payload).
- после `:` два константных `\x00`, между ними — статус.
- статус: 0x15 «стабильно», 0x04 «движение», 0x16/0x14 «пусто»;
  «стабильно» = младший бит == 1.
- масса: 32 бита little-endian, ЗНАКОВАЯ: `\x46\x05\x00\x00` = 1350 г,
  `\xfa\xff\xff\xff` = −6 г (дрейф пустой платформы, срезается в 0).

Проверка раскладки: 1350 г — `\x02\x0b:\x00\x15\x00\x46\x05\x00\x00\x00\x00\x00\x67`,
LRC = XOR(0x0B,':',0,0x15,0,0x46,0x05,0,0,0,0) = 0x67 ✓.
Пустая платформа (−6 г) — `\x02\x0b:\x00\x14\x00\xfa\xff\xff\xff\x00\x00\x00\x20`,
LRC = 0x20 ✓ (живой замер, 2026-10).

### Контрольная сумма (подтверждено в обе стороны)
**LRC = XOR всех байтов кадра после STX (не инвертируется).**
- Запрос: `\x05 ^ ':' ^ '0' ^ '0' ^ '3' ^ '0'` = 0x3C = `<` ✓
- Ответ: XOR байтов от `':'` до последнего байта данных включительно ✓

### Обнуление (setZero, из дизасма SelfServiceScales)
Тот же формат, третий байт `0x30` вместо `':'`:
```
→ STX '5' '0' '0' '0' '3' '0' LRC = \x02\x05\x30\x30\x30\x33\x30\x36 (8 байт)
```
LRC = XOR('5','0','0','0','3','0') = 0x36 ✓. Третий байт кадра — код
операции: 0x3A «:» — вес, 0x30 «0» — обнуление.

### Практические выводы для драйвера
- Обмен master-slave, таймаут ответа ~1 с; NAK/ACK и кадр приходят отдельными
  чтениями — собирать поток байтов и вырезать кадр от STX по байту длины.
- serialport-крейт на musl-сборке выставляет скорость через BOTHER — устройство
  молчит; порт открывать напрямую через libc termios (см. app/kiosk weight.rs).
- Опрос непрерывный: UI получает вес из фонового потока (weightChanged).
- Всё общение — ASCII-печатные байты + управляющие: логирование и отладка просты.

## 2. Принтер: ESC/POS (Epson page mode), `/dev/ttyS3`, 19200 8N1

Источник: живой дамп (strace, 3 этикетки идентичны) + дизасм старого ПО
SelfServiceScales (v2.0.2.65, Qt; класс Printer + ShtrihSlim; копия бинарника
и полная карта команд — temp/slim, выжимка здесь). Драйвер старого ПО —
тонкая обёртка над стандартным Epson ESC/POS, собственные команды только две
(0x1E 0x46/0x47, ниже).

### Инициализация (на этикетку)
```
ESC t \x11      кодовая страница 17 (в прошивке = CP866; «В» в дампе = 0x82)
ESC c 0 \x01    тип носителя: этикетка (gap-датчик включён)   [selectPaperModel(1)]
ESC { \x01      разворот 180° выключен
ESC L           вход в PAGE MODE
ESC T \x02      печать page mode, направление 2
ESC W 0,0,448,232   область этикетки 448 x 232 точки (label width=480,
                    labelFormat=1 — фактическая печать чуть уже)
CAN \x18        отмена предыдущих данных страницы
ESC 3 \x00      межстрочный интервал 0
ESC SP \x00     межсимвольный интервал 0
```

### Каждое поле = пара команд позиционирования + текст
```
ESC ! n / GS ! n   шрифт/размер (двойная высота для цен: ESC ! \x01)
ESC $ xL xH        горизонтальная позиция (X)
GS  $ yL yH        вертикальная позиция (Y, page mode)
<текст в CP866>    «ВИНОГРАД КИШМИШ ЧЕРНЫЙ КГ», «1,350», «199,99», «269,99»…
```
Наблюдённые Y: 0x40,0x64,0x73,0x86,0x94,0xA0,0xB4,0xD6 (двух-высотные поля
на 0x86/0xD6 — цены/итог).

### Штрихкод
```
GS k \x02 '210213601350' \x00    EAN-13, 12 цифр + NUL
ESC h/GS h — высота, ESC H/GS h HRI...
```

### Завершение
```
ESC ! / GS ! сброс размера, ESC { ..., затем ESC FF (\x1B\x0C) — печать
данных page mode; живой дамп завершается одиночным FF (\x0C) [printAndFeed]
```

### Подача и датчики (из дизасма)
```
GS FF (\x1D\x0C)   прокрутка до начала следующей этикетки по gap-датчику
                   [marksheetPositioning; у старого ПО — feedLabel]
DLE EOT n          статус в реальном времени; paper-байт = старший байт
                   статуса: 0 = этикетка снята → сигнал labelIsTakenOff
                   [checkLabelState опрашивает по таймеру 0.5 с]
```

### Сервисные настройки (однократно, сохраняются в памяти принтера)
```
RS F nL nH  (\x1E\x46, int16 LE, ≤400)  зазор «опто-датчик → печатающая
                                        линия» — conf optoThermoSpace
RS G nL nH  (\x1E\x47, int16 LE, ≤400)  откат (backspace) после выдачи
                                        этикетки — conf backwardSpace
```
Старое ПО шлёт их только из своего сервисного меню калибровки; в обычной
печати их нет — принтер применяет сохранённые значения сам после выдачи.
Значения машин: 172.32.0.5 — 362/75, боевая 192.168.41.129 — 375/80.

### Выводы
- label.xml **напрямую** транслируется в пару (ESC $, GS $) на каждое поле —
  визуальный редактор нового ПО может рендерить 1:1 как на экран (canvas),
  так и на принтер.
- Кодировка CP866 (code page 17; байты дампа: В=0x82, И=0x88 — таблица CP866,
  не CP1251) — новый редактор шлёт text в CP866 или переключает ESC t.
- Параметры conf старого ПО маппятся 1:1 на команды RS F / RS G (см. выше);
  для калибровки нового ПО достаточно CLI-команды, пишущей эти байты в порт
  принтера, живой принтер для дампажа больше не нужен.
- 19200 бод на этикетку с графикой — узкое место; скорость порта менять
  осторожно (настройка и на весах, и в принтере).

### Поведение/фичи старого ПО, отсутствующие в новом
1. **Лого на этикетке**: loadLogos при старте грузит два NV-изображения
   (FS q n <data>, буферы 288/384 байта в объекте драйвера); печать —
   EmbeddedImage-элемент label.xml (printDownloadedBitImage, FS p).
   → Бэклог нового ПО: печать лого магазина на этикетке.
2. **DLE ENQ n** (realTimeRequestToPrinter): восстановление после ошибки
   (n=1 recover / n=2 restart). У нового ПО нет — после paper-out принтер
   может остаться в error до пересброса питания.
   → Бэклог: после заправки бумаги слать DLE ENQ 1.
3. **executeTestPrint** = GS ( A 02 00 paper content — сервисный тест
   принтера (head/датчики), контент — gibberish «Варкалось…» для проверки
   всех глифов. Экран «Тестовая печать» старого меню.
4. **checkLabelState**: DLE EOT-опрос по таймеру 0.5 с после печати; paper=0
   → labelIsTakenOff → «этикетка снята». У нового ПО — фиксированный
   таймаут 5 с (DONE_TIMEOUT), снятие не ждём.
5. Экраны старого ПО: «Закончилась бумага в принтере», «Нет информации о
   товаре», «Версия» (ПО/прошивка), «Вес нестабилен», «Спасибо за покупку»,
   «отпечатанная этикетка снята», «Устройство не найдено».

### Зуммер/термобашня (эксперимент 2026-10-15)
Датчик термобашни есть (прошивка модуля пищит при открытии на боевых и
пищала на тестовых до замены образа), но в протокол он НЕ выставляется:
кадры веса (оба статусных байта), DLE EOT 1–7, GS r 1/49/65, ESC u/v,

Старый драйвер зуммером не управлял. Автокалибровка по открытию башни
невозможна; решение — ручная подача (GS FF) из меню настроек.

## 5. Расширенная карта POS2 весового модуля (источник: официальный
## тест Shtrih-M 2015 + JavaPOS equipment.jar + живые замеры 2026-10-15)

Источники: C-исходники официальной «Программы для проверки подключения»
(`audit/legacy-docs/test_weightscale-src/test_weightscale.c`, 2015),
JavaPOS-драйвер из боевой машины (`equipment.jar`, класс
`pa.equipment.scale.Pos2Serial`), живые замеры на 172.32.0.5.

### Формат кадра (общий, подтверждён C-кодом и живыми замерами)
```
STX(0x02) LEN <cmd> [данные...] LRC
LRC = XOR байтов от LEN до последнего байта данных включительно.
```
Длина кадра = LEN + 3 байта. LEN считается по байтам `cmd + данные`.
Ответ: ACK(0x06), затем `STX LEN <cmd-echo> <error=0 ok> [данные] LRC`.

### Коды операций (byte cmd после LEN)
| Код | Команда | Запрос | Ответ |
|-----|---------|--------|-------|
| 0x3A `:` | вес канала | `3A` + пароль (4 байта LE32) | state LE16 @4–5, масса LE32 signed @6–9, тара LE16 @10–11 |
| 0x30 `0` | обнуление | `30` + пароль 4 байта | подтверждение |
| 0x31 | тарирование | `31` + пароль | подтверждение (Java CMD_TARA) |
| 0x32 | установка тары значением | `32` + пароль + параметр | подтверждение (Java CMD_TARA_SET) |
| 0xFC | идентификация устройства | `FC` (пароль не нужен) | см. ниже |
| 0xE8 | свойства канала взвешивания | `E8` + номер канала | НПВ/НмПВ/дискреты, см. ниже |

Пароль: Java-драйвер берёт из параметра «Пароль»; в кадрах старого ПО —
ASCII `0030` (вес/обнуление работают с ним), C-тест 2015 шлёт нулевой
LE32. Оба варианта устройство принимает.

### 0xFC — идентификация (живой замер 2026-10-15, тестовые весы)
```
→ 02 01 FC FD                                  (без пароля, формат теста 2015)
← 06 02 29 FC 00 01 03 01 00 00 01 "SLIM   V5.0 20.06.2017 7 SHTRIH-M" FA
```
После `error=00`: 6 байтов полей (`01 03 01 00 00 01`), затем
строка-идентификация (Cp1251, 33 байта, формат "%.33s" с offset 10):
**прошивка весового модуля SLIM V5.0 от 20.06.2017**. Метод из
ремонтной документации для перепрошивки: mass-storage режим NXP
(перемычка J2 PRG → диск с firmware.bin) или FlashMagic по RS-232;
сам файл прошивки в открытом доступе отсутствует (поиск 2026-10-15).

### 0xE8 — свойства канала (карта ответа из test_weightscale.c)
Ответ после `error`: `power_of_ten` @7, max LE16 @8–9, min LE16 @10–11,
тара LE16 @12–13, range1 LE16 @14–15, range2 @16–17, range3 @18–19,
дискреты e: disk1..4 @20–23 (LE16). Масса/дискреты в граммах через
power_of_ten (−4 → г/10000 = кг при 0.1 г дискрете; −3, −2 аналогично).
На тестовых весах ответ на 0xE8 в формате C-теста (без пароля) — тишина;
с паролем — возврат блока идентификации (требует уточнения формата,
см. бэклог).

### Карта битов state в ответе 0x3A (из test_weightscale.c)
```
bit 0  — F (вес фиксирован/стабилен)
bit 1  — Z (нулевой уровень)
bit 3  — T (активна тара)
bit 4  — E
bit 5  — initial zero error (разгрузите платформу)
bit 6  — перегруз (overload)
bit 7  — ошибка калибровки
bit 8  — недогруз (underload)
bit 9  — аппаратная ошибка
```
Старший байт статуса (второй 0x00-байт кадра) — старшие биты этого LE16.

### Принтер: данные стенда (испытания 17–19.10.2026, VKP80II)
- Открытая термоголовка (датчик головки) АВАРИИ НЕ ДАЁТ: L4 остаётся
  валидным, печать продолжается. Аварийный флаг в L4 ставит клин бумаги.
- Клин бумаги (0x12 в L4) программно НЕ снимается: лестница
  DLE ENQ 1 → DLE ENQ 2 → ESC @ не помогает, подтверждено repeatedly.
  Снимается только выключением/включением питания принтера.
- Питание принтера и весов связано: выключение питания принтера на стенде
  потянуло за собой перезагрузку весов. При тираже питание принтера
  разделить с питанием основного блока.
- Ответ DLE EOT 4 (L4) валиден и стабилен; детект выдачи этикетки
  (label_in_tray по L4) срабатывает ~600 мс после задания.
- Датчик зазора (Gap sensor) по командам статуса недоступен:
  DLE EOT 1-4 статичны, ESC v / GS r / DLE DC4 молчат, ASB (GS a) не
  поддержан. Длину этикетки меряем временем подачи FF (см. спеку
  label-designer, [printer] ff_offset_ms / ff_ms_per_mm).

### Протокол: подтверждено пробником (counterprobe, 19.10.2026)
- **Пробник требует DTR|RTS** — без модемных линий TX принтера молчит.
  Это и было причиной «тишины» shell/python-проб: stty/termios не
  поднимают DTR/RTS по умолчанию. Рабочий путь — serialport crate,
  как в демоне.
- DLE EOT 1..4 отвечают: 0x00 / 0x12 / 0x12 / 0x1E (при рулоне
  near-end и этикетке в лотке). Раскладка битов — HPRT-мануал:
  EOT4: bits2-3 (0x0C) near-end, bits5-6 (0x60) paper not present,
  фиксированные биты 0x12. Наша эмпирика l4_fault/label_in_tray
  согласуется с официальной картой (0x72 = paper not present,
  0x1E = present: этикетка в пути/лотке).
- EOT4 = 0x1E: рулон на стенде почти закончился (near-end) — при
  визите заменить рулон.
- DLE EOT 17, 20 (print/FULL status) — НЕ поддержаны (тишина).
- Счётчики: 1D E1 (остаток), 1D E2 (резы), 1D E3 (напечатано, см),
  1D E4 (втягивания), 1D E5 (включения), GS g 0/2 (Epson maintenance)
  — ВСЕ молчат. Прошивка HPRT сервисных счётчиков не экспортирует.
- US-команды Custom (1F ...) — НЕ поддержаны.
- Плотность печати: команды нет в HPRT-наборе (1D 7C из мануала
  Custom недоступна). Качество печати регулируется только локально
  через self-test/setup принтера (если он есть у PT561 — проверить
  клавиши при включении на месте).
- GS r → 0x03 (near-end), ESC v → 0x00 (paper present) — работают.
- GS a (ASB) заявлена в HPRT-мануале (4-байтный формат) — прежний
  вывод «ASB не поддержан» требует перепроверки (смотрели не тот
  формат ответа).
- Вывод по программному трекингу пробега: счётчиков прошивки нет —
  трекер строится только на своих данных (print_log + время FF).

### Уточнение по «клину 0x12»
- По HPRT-раскладке 0x12 в L4 = фиксированные биты (норма). Ранее
  «0x12 = клин» относилось к другому уровню/моменту. Авария по HPRT:
  L4 bits5-6 (0x60) = paper not present; перегрев головки — L3 bit6
  (0x40, auto-recoverable); каттер — L3 bit3 (0x08). Перегрев
  снимается сам по остывании (мануал HPRT).

### Аппаратная ограничение: кнопок НЕТ (зафиксировано 19.10.2026)
- На корпусе киоска и принтера физические кнопки отсутствуют. Самотест
  и setup принтера «клавишами при включении» (LF/FF мануала Custom)
  недоступны — эта рекомендация закрыта.
- Следствие: всё конфигурирование принтера — ТОЛЬКО через serial-команды
  и ПО киоска. Что не выразимо командами (температура/напряжение головки
  в self-test, локальная калибровка качества) — недоступно совсем,

- Для тиража: сервисный инженер подключается к порту принтера своим

  отдавать диагностику сам (экран «Оборудование → Принтер»).
