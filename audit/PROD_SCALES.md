# Боевые весы 192.0.2.50 — ревизия и сверка слабых мест

Только чтение, 2026-10-14, по SSH через jump-хост (см. STATUS.md). Дополнение к
`AUDIT.md`/`PROBLEMS.md` (составленным ранее на этой же модели ПО). Здесь —
подтверждение фактуры на действующей машине и находки, которых в старых
документах нет. Секреты и адресные данные в документ не перенесены.

## 1. Состояние машины

- Ubuntu 16.04 LTS, kernel 4.4.0-28-generic, hostname `scales`, X11 (startx из rc.local).
- Диск `/` 25 ГБ, занято 3.7 ГБ; RAM 4 ГБ. enp3s0 = 192.0.2.50/24 (статика).
- Слушают: sshd (22), vsftpd (21), x11vnc (5900, пароль REMOVED открытым текстом в `.xsessionrc`).
- Версия ПО: v.2.0.2.65.48dd52d — та же, что в `AUDIT.md`.

## 2. Живой конвейер данных (подтверждено метками времени)

1. root-crontab, установлен 2018-08-02: `*/30 * * * * bash /sync/syncfiles/syncstart.sh`.
2. `sync.x`: `lftp` → FTP центра (креды `pos:REMOVED` в открытом виде) → `mirror MappleTouch/` в `/sync/MappleTouch/`.
3. `syncstart.sh`: `rsync -d MappleTouch/ /var/ftp/scale/` → `echo '' >> ready.flg`. Проверок кодов возврата нет.
4. DataUpdater внутри приложения видит флаги, импортирует `plu.xml`/`layout.xml`,
   копирует все `*.jpg` в `sss/img/`, архивирует исходники в `sss/history/<дата-время> <файл>`,
   после чего **удаляет из `/var/ftp/scale` импортированные xml и флаги** (bmp и картинки остаются).
5. На каждое обновление приложение **перезапускается само** («New data found. Updating database...» →
   два подряд «Application starting...» с интервалом ~0.4 с — падение на занятом порте и повторный
   старт в цикле `while true`). Покупатель в этот момент видит пустой/перезагружающийся экран.
6. Импорт только при изменении файлов: обычно 2 импорта в день (утро/день), хотя cron срабатывает 48 раз.

## 3. Данные товаров (фактура на сегодня)

- `plu.xml`: 215 товаров; поля `plunumber, price (копейки), itemcode, namefirst,
  namesecond, groupcode, shelflife`. `actionprice` не приходит вообще (0 упоминаний).
- `groupcode` у всех 215 товаров = «21» — поле фактически мёртвое; реальная
  группировка — только из `layout.xml` (5 групп, 215 кнопок = 215 PLU, паритет полный).
- `shelflife` в US-формате `MM/DD/YYYY HH:NN:SS` — новый парсер должен это учитывать.
- `sss/img/`: 2465 файлов, из них **879 (36%) — мусор**: `*.jpg.jpg`, `XXX (2).jpg`,
  `*.gpg.jpg`, случайные фото (`photo_2023-03-10...jpg`, русские имена), `*.png`.
  Приложение копирует **все** `*.jpg` без разбора имён; `rsync` без `--delete`,
  поэтому дубли и старьё копятся годами и перекачиваются при каждом импорте.
- `/var/ftp/scale/`: 27 файлов `*.bmp` по 144718 байт (одинаковый размер = один
  формат 378×378), md5 у всех разные — содержательные картинки (вероятно, для
  этикеток/логотипов), доставляются тем же потоком.
- `sss/history/`: **16 677 файлов с 2018-09-20** — архив импортов без чистки.
- `label.xml` от 2017-12-28 — не синхронизируется (правится вручную), содержит
  реквизиты магазина и схему печати (см. `AUDIT.md` §Данные).

## 4. Лог и ошибки порта

- `SelfServiceScales.log` = 1.3 ГБ, 22.8 млн строк, без ротации. По `.bash_history`
  лог уже вручную удаляли (`sudo rm`) из-за места — вырастет снова.
- 19.5 млн строк (85%) — поток `Copying: "файл.jpg"` на каждый импорт: лог
  практически неинформативен.
- `Scales port error: <код>` — спорадические (порядка сотни с 20.01.2026,
  ≤6 в день, коды 0 и 9, последнее 12.02.2026), самовосстанавливаются — это
  «штатные» хрипы опроса порта, не авария. `Cannot open img` = 0 (картинки
  сейчас догнаны; ранее это была главная циклическая ошибка).
- `Cannot open img` сейчас 0 — набор картинок соответствует выгрузке; но при
  добавлении товара с запаздывающей картинкой ошибка вернётся (механизм прежний).

## 5. Калибровка принтера дрейфует между машинами и во времени

`backwardSpace/optoThermoSpace`: аудит (другая машина) 75/362 → боевые сейчас
80/375 → бэкап `SelfServiceScales.conf.Lh2685` (2019) 78/382. Подгонка вручную,
партии этикеток/износ датчика сдвигают значения — подтверждает требование
калибровки из GUI (П.А1 в `PROBLEMS.md`). Прочий мусор: `.Lh2685`-бэкап,
upstart-артефакт `~/scales.conf` с опечаткой `end srcript` (не работает, игнорируется systemd).

## 6. Безопасность (фактическое состояние)

- VNC-пароль REMOVED открытым текстом в `.xsessionrc`, порт 5900 наружу в LAN магазина.
- FTP-креды центра `pos:REMOVED` в `/sync/syncfiles/sync.x`.
- sudo-пароль администратора напечатан в `.bash_history` (оператор вводил его в
  интерактиве; значение совпадает с SSH-паролем весов).
- vsftpd: `userlist_enable=YES` + `userlist_deny=NO`, но `/etc/vsftpd.userlist`
  отсутствует — поведение на усмотрение версии vsftpd; конфиг не самодостаточен.
- Отдельные подтверждения из `PROBLEMS.md` §Г: FTP с записью, пароли в скриптах.

## 8. Что обязано уметь новое ПО (протокол совместимости с центром)

1. **Drop-режим**: центр пушит файлы в приёмный каталог (сейчас `/var/ftp/scale`
   по FTP) — `plu.xml`, `layout.xml`, `<PLU>.jpg`, `<код>.bmp`; триггеры
   `ready.flg`/`uploading.flg`. Новый киоск это уже умеет (STATUS.md, синхронизация).
2. **Pull-режим как запасной**: внутренний таймер вместо cron+lftp, тот же
   FTP-источник (192.0.2.60, `MappleTouch/`) — чтобы переезд не требовал
   изменений на стороне центра.
3. **Парсер plu.xml**: price в копейках; shelflife `MM/DD/YYYY`; `actionprice`
   опционально (сейчас не приходит); groupcode игнорировать (мёртвое поле),
   группировку брать из layout.xml.
4. **Картиночный поток с мусорофильтром**: принимать только имена вида
   `<число>.jpg` (PLU), остальное — в карантин/отчёт; не тащить дубли и мусор.
5. **Архив импорта** с таймстампом (аналог `sss/history/`) — но с лимитом
   глубины/ротацией, не 16k файлов за 8 лет.
6. **Применение данных без перезапуска** приложения (живая замена моделей — уже
   реализовано в новом киоске).
7. Имена устройств: `/dev/scales` (udev-правило NXP 1fc9:80a3) и `/dev/ttyS3`
   (принтер) — переносится в config.toml; калибровка — в БД/GUI.
